Shared Memory

Overview

shared_memory() gives the swarm one board of files that every member reads and writes with a shared_memory tool. The tool has the commands of Inspect’s memory() tool, over files under /shared_memory, and one more, append. Every write goes through the swarm as a record from the member that made it, so the log keeps the board’s whole history, and members hear about each other’s changes.

Members that get shared_memory also get swarm_wait, so a member that needs a peer’s work waits instead of polling. Each sample has its own board, which is gone when the swarm ends.

examples/shared_memory.py is a runnable swarm that splits a count between members, who share their parts on the board and wait for each other.

Wiring

Members get the tool from swarm_tools(), which gives a member the tools of the swarm’s channels. Call it inside a member builder registered with @agent, and pass the builder to member() without calling it:

from inspect_ai.agent import Agent, agent, deepagent, react
from inspect_ai.tool import bash

from inspect_swarm import (
    filesystem,
    member,
    shared_memory,
    swarm,
    swarm_tools,
)


@agent
def solver_member() -> Agent:
    return react(tools=[bash(), swarm_tools()])


@agent
def reviewer_member() -> Agent:
    return deepagent(tools=[bash(), swarm_tools()])


solver = swarm(
    members=[
        member(solver_member, name="solver", count=3),
        member(reviewer_member, name="reviewer"),
    ],
    channels=[filesystem(), shared_memory()],
)
  • The log records a builder by name and arguments, so the swarm can be rebuilt from the log. It cannot rebuild swarm_tools() passed in args or inside an agent you built (Members).
  • Any agent that takes a ToolSource in its tools can take swarm_tools(). It gives no tools when the swarm has no channel with tools, or outside a swarm, so one member definition serves every arm of an experiment.
  • This swarm keeps the filesystem channel beside the board. channels=[shared_memory()], or channels=["shared_memory"], replaces it: members still share the sample’s sandbox, but their preamble no longer mentions /shared. Members with their own sandboxes can use the board with no shared volume.
  • The channel needs member names that start with a lowercase letter, followed by at most 47 lowercase letters, digits, _ or -.
  • A bridged member gets the tool from swarm_bridged_tools(["shared_memory"]). Its CLI is one agent to the board: a file any of its conversations viewed counts as viewed by all of them (Bridged members).

The tool

The shared_memory tool’s commands are view, create, str_replace, insert, append, delete, rename and changes. Paths are /shared_memory followed by up to eight components of letters, digits, ., _ and -.

  • Each file has an id, such as f-3, which it keeps through renames. Status lines and swarm_wait results name files by id. view takes an id as file_id, in place of path. A view shows the file’s path, which the write commands take.
  • A file view shows the file inside a <peer_file> fence that names its id, path, version and last writer. A directory view lists every file under it at any depth, with its id, version and last writer.
  • Write commands return a short acknowledgment, not the file. View a file to see it.
  • Every result ends with a status line naming the files other agents changed since this loop last viewed them, such as Shared memory: 2 files changed since you last viewed them (f-2, f-9). It names at most 10 files and counts the rest, as in (f-1, ..., f-10, and 2 more). With the messages channel, a result in the member’s own loop then ends with its count of unread messages, when any remain.
  • changes returns the board’s status line, naming every changed file, or Shared memory: no files changed since you last viewed them., so a loop can check for news without viewing anything. Like the status line, it marks nothing seen. With messages, its result in a member’s own loop also ends with the unread count, when any remain.

Fences are labels

A fence is a label for the reader, not a security boundary. A member can write text that looks like a fence, another member’s file, or text the swarm writes, such as a status line. The swarm does not refuse or clean such text.

What holds:

  • Members see each other’s text only in tool results.
  • The record of the board comes from the swarm’s own events and ids, never from the text of a result (The record of the board).

An experiment that needs stronger guarantees, such as a study of members that deceive each other, needs a channel that provides them (Writing a channel).

The seen rule

A loop must view a file in its current version before it overwrites it with create, inserts into it, renames it or deletes it. A write to a file changed since the loop’s last view is refused with an error that names the file and its last writer, and the loop views it and retries. So no member overwrites a change it has not seen.

Two commands need no view:

  • str_replace fails unless old_str occurs exactly once in the file as it is when the write lands, so it is safe without one.
  • append adds text on a new line at the end of the file as it is when the write lands, and creates the file if needed. It suits a log or list that many members write to.

Hearing about changes

The swarm adds no messages to a member’s conversation. A member learns what other agents changed only through its tools:

  • The status line at the end of every shared_memory result. With the messages channel, a result in the member’s own loop then ends with its count of unread messages.
  • shared_memory(command="changes"), which returns the board’s status line, naming every changed file, to check for changes without viewing anything.
  • swarm_wait, which blocks until a file the member watches changes (Waiting for other members).

A changed file stays in the status line until the loop views it. A deleted file is listed only to a loop that previously viewed or wrote it, including a blind append. These lists hold counts, file ids and member names, never a file path or file contents.

Waiting for other members

swarm_wait blocks until there is something for the member to look at:

  • A file it watches has a change that the waiting agent did not write and has not viewed. It watches one file with file_id, a file or directory with path, or the whole board with neither. A subagent’s write counts, so a member can wait for its own subagents.
  • Another member has ended.

It returns at once if that is already so, and keeps returning while such a file stays unviewed. Its result names the changed files by id and the ended members by name and status, never file content: the member views a file to read it.

A wait also ends without news: when every member is waiting, has ended or has not started; when the swarm stops; when the member’s own agent finishes; or after timeout seconds. max_wait sets the longest wait and the default timeout, 600 seconds unless you change it, for example shared_memory(max_wait=300).

A wait is time inside a tool call. It counts towards the member’s time limit, the swarm’s time cap and the sample’s time and working limits. It makes no model call, so it adds no tokens, cost or steps. The metrics report each member’s waits, their time, and its idle_time: the seconds the member did nothing but wait (Analysis).

A swarm with only the filesystem channel, or channels=[], has no swarm_wait: there is nothing it could wake on.

Subagents

A member’s subagents read and write the board as the member. deepagent’s general() subagents, synchronous and background, and any nested loop given swarm_tools(), get the shared_memory and swarm_wait tools.

The member’s agent decides which subagents get swarm_tools(). deepagent’s general() inherits the member’s tools, so it gets the board. research() gets its own read-only tools instead, and has the board only when you pass research(extra_tools=[swarm_tools()]).

  • Their writes are records from the member. The evidence also names the loop that made each write or read, and marks a subagent’s as nested.
  • Each loop has its own view of the board: the seen rule and the status line apply to the loop that calls the tool.
  • A member’s subagents share its write rate, so they cannot multiply its write volume.
  • A subagent’s wait counts in the member’s wait_time but not its idle_time.

A deepagent member also has a private memory() of its own by default. Pass deepagent(memory=False) when the board should be its only memory tool.

Limits

The board is bounded:

Argument Default Limit
max_files 10,000 Files on the board
max_file_bytes 1,000,000 UTF-8 bytes in one file
max_file_lines 100,000 Lines in one file
max_board_bytes 100,000,000 UTF-8 bytes in all files together
rate (60, 60.0) Writes per member, all its loops together, in a sliding window of seconds; None for no limit
max_wait 600 The longest swarm_wait, in seconds, and its default timeout

A write that would pass a limit is refused with an error that says which. Once the swarm begins to stop, writes are refused and views still work.

The record of the board

The swarm logs the members’ writes, views and waits as CommunicationEvents with source inspect_swarm. Each is in the span of the tool call that made it, and its kind is one of:

  • sent: a write that reached the swarm, with its payload in send.record.content, why it was refused in send.rejected if it was, and its operation in data["record"]["op"].
  • delivered: a write applied to the board, with its commit sequence number in delivery.seq and each file’s previous and new version in data["result"]["files"]. Replaying the delivered writes in sequence order rebuilds every version of the board.
  • read: a view or a listing. record_ids names the record that last wrote each file at the version shown, and data has each file’s version. data["depends_on"] names the records the result depends on: for a view, every write in the file’s history; for a deleted file’s id, the delete; for a listing, none.
  • waited: a swarm_wait call, with what ended it and how long it took in wait, and in data["depends_on"] the write it reported for each changed file.

Each event names the member that acted (agent) and its loop (loop_span_id). The record_ids of a write’s sent and delivered events and of the reads of what it wrote are the same id. depends_on names each record once per loop: a record that an earlier result of the same loop depended on is left out. The metrics count these events for each member.

Monitoring with Inspect Sentinel

A native member’s call to shared_memory is an ordinary tool call, so Inspect Sentinel’s tool stages see it with no swarm code. A protocol at BeforeToolCall can reject a write before it reaches the board, and one at AfterToolCall sees exactly what a view is about to show. For example, a rule that keeps credentials off the board:

from inspect_sentinel import (
    BeforeToolCall,
    Context,
    Decision,
    Escalations,
    Protocol,
    call_text,
    find_words,
    protocol,
)


@protocol
def no_secrets_on_board() -> Protocol:
    """Reject shared_memory writes that mention a credential."""

    async def decide(
        context: Context, step: BeforeToolCall, escalations: Escalations
    ) -> Decision | None:
        if step.call.function != "shared_memory":
            return None
        if step.call.arguments.get("command") == "view":
            return None
        used = find_words(call_text(step.call), ["password", "api_key", "token"])
        if used:
            return Decision.reject(
                f"write mentions {', '.join(used)}",
                message="Credentials may not be written to shared memory.",
            )
        return Decision.proceed()

    return decide

Pass it to the task as Task(..., sentinel=no_secrets_on_board()). The member gets the decision’s message as the tool call’s error. A step’s conversation is the agent span id of the loop that made the call, and each CommunicationEvent names that loop in loop_span_id, so the two can be joined. Sentinel does not run on bridged tool calls; use the bridge’s approval policies for those calls.

Migrating from memory(instance=...)

Before this channel, a board shared on purpose was a memory() tool with an explicit instance in every member’s tools, memory(instance="board"), with the prompt saying it is shared. That still works, and it is a different channel: members’ ToolEvents record its use, with no sender, fence, status line, bounds or CommunicationEvents. Nothing refuses using both; an arm that wants the board as its only channel gives no two members a shared instance.

To move a task to the channel:

  1. In the member builder, replace memory(instance="board") with swarm_tools() in the tools. The builder stays a registered @agent.
  2. For a deepagent member, pass memory=False to keep one memory tool as before, or leave deepagent’s private memory() as an extra notebook per member. These are different experimental conditions.
  3. Replace the instructions that described the board with "shared_memory" or shared_memory(...) in channels=. Its instructions go in each member’s preamble.
  4. Change the prompt’s tool and path names (memory, /memories) to shared_memory and /shared_memory.

What changes for the members:

  • Overwriting with create, insert, delete and rename need a current view (The seen rule), and append adds an entry at the end of a file without one.
  • Writes return an acknowledgment, not a snippet of the file.
  • A directory view lists every file under it at any depth, and there are no empty directories.
  • Paths are narrower, files and the board are bounded, and tabs are kept.
  • Views are fenced and name the last writer, and status lines report changes.

An eval set comparing the two boards runs them as two arms: the channel list and the builder’s arguments differ, so their task identifiers do. examples/proof_swarm.py is shaped like such a port: members with their own sandboxes whose only channel is the board.
