# Inspect Swarm: auditing the filesystem

## Overview

With `channels=[..., "filesystem_audit"]`, the swarm records every change to the files members work on: which file, when, what it now holds, and, when the change was in a member's own sandbox, that member. It adds no tools and says nothing to members. When the swarm starts, before any member does, it starts a small Python watcher in each sandbox the members use, running as the sandbox's default user. The watcher takes a baseline of the watched directories, then rescans them every second and streams each change back to the swarm: a file written (with its new content, or a diff against the version the audit last recorded, up to a byte cap), renamed or deleted, with its size, its hash and the interval in which the change happened. The swarm writes each change as an evidence event and counts them in the swarm's metrics. When every member has ended, it asks each watcher for a final scan and stops it. A watcher that dies or stops answering is not restarted: that sandbox's audit ends there, and the record says it is incomplete, as it does when the swarm could not record a line the watcher wrote. The design relies on a short list of guarantees from inspect_ai's remote-process API, specified and built there: other tasks keep their sandbox events while the audit's are suppressed, the audit's calls write no raw output into the transcript, a normal stop delivers every line the watcher wrote, and cleaning up a remote process returns within a stated time, even when the process's exit cannot be confirmed.

A change in a member's own sandbox (`member(sandbox=...)`) is labelled with that member. The label names the sandbox's member, not a proven writer: the member's tools, scripts and leftover processes write there, but so can the swarm's controller, another swarm using the same environment, or anything else in the sample, and the audit cannot tell them apart. In one sandbox the members share, and in a volume their sandboxes share, nothing in the sandbox says which member wrote a file, so those changes are recorded with no member; the time and content are still there for analysis to set against the members' tool calls. Polling misses what happens between two scans (a temporary file created and removed, intermediate versions of a file), and the audit says so in its own records. Reads are not tracked.

## Why

What an analysis of a swarm needs from its log is who wrote which file, when, and what they wrote. Today the log has the members' tool calls and nothing else: shared files are "observed, not recorded", and processes a member starts "can read and write files between logged tool calls, and after the member has ended" ([Channels: Shared files are observed, not recorded](../docs/channels.qmd#shared-files-are-observed-not-recorded)). The communication design leaves "instrumentation in the sandbox" to later work ([swarm-communication.md Not this design](swarm-communication.md#not-this-design)).

In an internal user's experiment runs the most important file changes were made by a command, a redirect or a script, so their content is in no tool argument. A `bash` call such as `python3 prove.py > out.txt` records the command, not what `out.txt` holds or that `prove.py` rewrote `lemma.lean` on its way. In a shared sandbox, which the first internal user ran ([swarm-wait.md](swarm-wait.md#who-waits-today)), nothing records which member's command it was either.

## Goals and non-goals

Goals:

- A `@swarm_channel` factory, `filesystem_audit()`, with plain-value configuration that logs faithfully, adds no tools and no instructions, and records changes to files under configured directories in every sandbox the members use.
- For each change: its kind (written, renamed, deleted), path, time bounds, size, hash, and the new content or a diff, under byte and event caps; the member whose own sandbox it happened in, when there is one; never a proven writer.
- An honest statement, in the design and in each run's records, of what it misses.
- How the events appear in evidence and metrics, and how they relate to the filesystem channel and to users isolation.
- Answers to the issue's questions: providers and images, caps and paths, reads, and whether `users()` is a prerequisite.

Non-goals:

- **Attributing changes in one shared sandbox or a shared volume.** It needs to know the writing process, which no unprivileged facility gives ([Attribution](#attribution-by-topology)).
- **Reads.** Not tracked, now or as a planned step ([Reads](#reads)).
- **Containment or tamper resistance.** A member with root in its sandbox can blind or confuse the audit; it measures what members do, it is not a boundary ([Security](#security)).
- **Showing changes to members**, as notices or tool results. The audit only records; telling members about it would be a treatment.
- **Building users isolation** ([swarm-sandbox-isolation.md](swarm-sandbox-isolation.md)), or changing the `filesystem` channel.

## Current behaviour

Paths are relative to each repository's root; `src/inspect_ai/...` and `src/inspect_sandbox_tools/...` are in inspect_ai. Claims marked *(spike)* were checked by running an Inspect eval on mockllm with the `docker` sandbox and `python:3.12-slim`, in a throwaway script; nothing from it is committed.

### The filesystem channel has no records

- `filesystem()` is an instructions-only channel: `FilesystemChannel` overrides `instructions()` only, so its `name`, `prefix` and `open()` keep `Channel`'s defaults, `None` (`src/inspect_swarm/_channel/filesystem.py:10-32`, `src/inspect_swarm/_channel/_channel.py:35-70`). It writes no evidence and opens no state. How the audit's events relate to the filesystem channel's existing records therefore has a short answer: there are none; this channel is the instrumentation the communication design's observation limit asks for.
- With `shared_volume=True` it describes per-member sandboxes that each mount one volume at `shared`, an absolute path, and the swarm cannot check that the volume is mounted (`filesystem.py:35-85`). `_swarm.py` already reads the channel's `shared_volume` to choose the preamble and to check the topology (`src/inspect_swarm/_swarm.py:149`, `:313-350`).

### Channels, the bus and the runtime

- `Channel.open(run)` returns a per-run `ChannelState` or `None`; `ChannelRun` carries the run's bus and roster (`_channel.py:61-92`). The bus calls `open()` for every channel in its constructor and refuses a state from a channel with no `name` or `prefix` (`src/inspect_swarm/_bus/_bus.py:68-84`); `SwarmRun` builds the bus in its constructor, before any member starts (`src/inspect_swarm/_controller/_control.py:265-269`).
- `Bus.deliver()` is for records a member's tool call makes: it raises outside a member (`_bus.py:220-226`), and its steps are storm controls, `sent`/`delivered` evidence and the channel's `apply()`.
- A channel with a `name` is a bus channel, and a bridged member is refused beside one (`_swarm.py:273-310`). Instructions-only channels are accepted beside bridged members.
- `SwarmRun.run()` sets the swarm's start, enters the caps, runs the members' task group (inside which the controller starts members), then the final step, and in a `finally` writes the ledger and the metrics (`_control.py:380-525`). There is no hook for work that must run beside the members for the whole run.
- The time cap is a timer started inside the members' task group that sleeps the cap's full length and then stops the swarm (`_control.py:417-424`, `:642-644`), while `swarm_budget()` reports time used from the swarm's start (`src/inspect_swarm/_budget.py:695-697`). Anything the run does between setting its start and starting that timer delays the stop by as long. A member that never started is a supported shape: it ends `pending`, with no status ([Analysis](../docs/analysis.qmd)).

### Evidence and metrics

- Evidence is an `InfoEvent` with `source="inspect_swarm"` and a payload of `version`, `type`, `kind`, `member` and `span_id` plus fields, never member text in harness-written lines (`src/inspect_swarm/_evidence.py:20-43`). The ledger's `EventLog` collects the `comm` events live from the transcript (`src/inspect_swarm/_ledger.py:318-327`), and `swarm_metrics()` counts them into per-member `CommMetrics` (`src/inspect_swarm/_metrics.py:19-35`, `:274-302`).
- The `EventLog` is subscribed to the whole sample's transcript for the swarm's interval (`src/inspect_swarm/_ledger.py:368-372`), so it also receives a nested swarm's events: a member may run a swarm of its own (`tests/test_background_members.py:1103-1136`). `comm` events are kept to the swarm's own by their `member`, since member names are unique in a sample (`_metrics.py:271-274`). Nothing else identifies a run: `SwarmRun` has no id of its own, and the span `SwarmRun.run()` records as the swarm's (`src/inspect_swarm/_controller/_control.py:384-389`) is the caller's current span, which the swarm does not open. A swarm called through inspect_ai's `run()` gets an agent span of its own, but one called directly (`await swarm(...)(state)`, as `tests/test_metrics.py:395-397` does, or by a controller) does not, since `@agent` opens no span for a direct call; so two swarms called concurrently from one solver, or a controller's direct call of an inner swarm, share one span.
- `MemberMetrics` and `SwarmMetrics` already carry harness-validity lists (`never_acted`, `notify_unwired`, `tools_unwired`) and give every newer field a default, so older metrics still load (`_metrics.py:37-111`).

### Sandbox topologies and who uses each

The topologies are described in [Sandboxes](../docs/sandboxes.qmd). Who uses each, and what it means for the audit:

- **One shared sandbox** ([Shared](../docs/sandboxes.qmd#shared)), the default. The first internal user ran a leaderless swarm there with the `filesystem` channel ([swarm-wait.md Who waits today](swarm-wait.md#who-waits-today)); `examples/shared_sandbox.py` is the same shape, whose `examples/compose.yaml` sets no working directory, so commands start in `/`. Members run as the sandbox's default user, root in these images.
- **A sandbox per member** ([Per member](../docs/sandboxes.qmd#per-member)). - **A shared volume** between per-member sandboxes, with `filesystem(shared_volume=True)` ([A shared volume](../docs/sandboxes.qmd#a-shared-volume)). Tested at construction (`tests/test_member_sandboxes.py:280-345`); no example or known user runs one.

- No package in the satellite checkouts beside this one (inspect_ai, inspect_evals, inspect_swe, inspect_flow, inspect_scout, inspect_sentinel) imports inspect_swarm.

### Running a long-lived process in a sandbox

- `SandboxEnvironment.exec_remote()` starts a command through the injected sandbox tools, injecting them first if needed (`src/inspect_ai/util/_sandbox/environment.py:374-450`). With `ExecRemoteStreamingOptions(stdin_open=True)` the host can write to the process's stdin and close it later (`exec_remote.py:160`, `:573`); `kill()` terminates it (`exec_remote.py:604`), so work the process should do before it exits has to be asked for through stdin. Docker and Kubernetes both use this base implementation; inspect_k8s_sandbox does not override it. `local` runs commands on the host.
- **Its user.** With no `user`, the process runs as the sandbox's default exec identity, the one `exec()` uses with no `user`: `_start()` sends `tools_user_param()`'s value, the sandbox's `_tools_default_user` (`exec_remote.py:356`, `src/inspect_ai/util/_sandbox/_cli.py:36-49`). The root identity the tools may hold is only the RPC wrapper's (`exec_remote.py:316-324`).
- The host polls the process for output. The first poll is immediate; a poll that returns output is followed at once by the next one when the caller asks for more, and only a poll that returns nothing waits the poll interval, at least 5 seconds whatever the sandbox's own interval (`MIN_POLL_INTERVAL = 5`, `exec_remote.py:224`, `:290-291`, `:403-438`). So a process that writes often is polled more often than every 5 seconds. A poll returns at most 1 MiB, and the tools server buffers up to 100 MiB of output before a write by the process blocks (`src/inspect_sandbox_tools/src/inspect_sandbox_tools/_remote_tools/_exec_remote/_job.py:34-35`).
- **Event suppression is per proxy.** Polls run inside `SandboxEnvironmentProxy.no_events()`, which sets a flag on the proxy every task shares, so a member's command that finishes during a poll loses its `SandboxEvent` (`exec_remote.py:479`, `src/inspect_ai/util/_sandbox/events.py:223-229`). *(spike: 150 concurrent `exec(["true"])` calls beside a polled watcher left 140 `SandboxEvent`s.)*
- **Lifecycle calls log raw output.** The start, `close_stdin()`, `kill()` and the iterator's clean-up on cancellation run their RPCs outside `no_events()`, and the proxy logs each RPC's response, the process's queued stdout and stderr included, as a `SandboxEvent` (`exec_remote.py:196-218`, `:573-627`; `events.py:99-116`).
- **The handle's lifecycle.** The iterator polls until there is output, kills the process only when its task is cancelled, and raises, leaving the process running, when a poll fails after its retries; `kill()` swallows a failed RPC, so its return does not confirm an exit (`exec_remote.py:403-444`, `:604-627`).
- **Its waits are not bounded today.** Each request has a 120-second timeout that the sandbox retries, and the iterator's clean-up awaits `kill()` shielded, so cancelling an iterating task can take minutes (`exec_remote.py:113-123`, `:316-336`, `:440-443`).
- **Output can be lost or repeated around `close_stdin()`.** Its returned output and the iterator's polls share one unsynchronized queue and acknowledgement, so output `close_stdin()` returns can be overwritten by the next poll and never reach the iterator, or a chunk (up to 4,096 bytes, anywhere in a line) can be yielded twice (`exec_remote.py:395-438`, `:573-602`).

### What a watcher in the sandbox sees *(spike)*

A Python stdlib watcher, started with `exec_remote()` on `python:3.12-slim` and given its program on stdin, took a baseline of `/work` and rescanned it every 0.5 s. It reported, with content: a file written by `echo hi > a.txt`; a log appended to three times in a loop (one event, the final content); a file a `python3 -c` command wrote; an existing file overwritten; `a.txt` renamed to `b.txt` (matched by inode); the log deleted; and a file a `nohup` background process wrote two seconds after its tool call had returned. It did not report a file created and removed in one command, and skipped the excluded `.git`. Its events arrived at the host up to 5 s after its own timestamps, one poll interval. Closing its stdin made it run a final scan, report, and exit 0. The same program, run with `docker run` on `python:3.8-slim` (Python 3.8.20), reported a write, a rename and a deletion. `python3` with `ctypes`, `hashlib` and `difflib` is in `python:3.12-slim` and in `aisiuk/inspect-tool-support`; `inotifywait` is in neither.

### What ownership says under users isolation

A file's owner is the user that created it, and writing to an existing file does not change its owner. swarm-sandbox-isolation.md's census relies on exactly that ("A file's owner is its creator") and says what it cannot see: "reads, ... modifications of existing files" ([What the topology makes measurable](swarm-sandbox-isolation.md#what-the-topology-makes-measurable)). Its survey finds no unprivileged facility that reports which process made a change: process-level tracing needs `CAP_SYS_ADMIN` or similar, which default containers and gVisor do not give ([Survey](swarm-sandbox-isolation.md#survey-linux-isolation-inside-one-sandbox)).

## Design

### At a glance

```
 swarm start                       during the run                          swarm end
 ───────────                       ──────────────                          ─────────
 for each watched sandbox:         watcher (in the sandbox, python3):      every member ended
   probe: python3, cwd, clock        every `interval` s: scan, diff,       for each watcher:
   exec_remote(watcher) ──────────►  print one JSON line per change          close stdin ──► final scan, "done", exit
   wait for "ready" (baseline)     host poller (5 s when idle):            write audit_ended
 then the controller starts          read lines, attribute, cap,           metrics count the fs events
 members                             write `fs` evidence
```

| Topology | Watchers | `member` of a change |
|---|---|---|
| A sandbox per member | one in each member's sandbox | that member |
| ... and a shared volume, `filesystem(shared_volume=True)` | also one for the volume, in the first member's sandbox; the members' own watchers skip it | none |
| One shared sandbox | one, in the caller's current default sandbox (the sample's default at the root) | none |

The shared sandbox and a declared shared volume are recorded in the first version, with `member: null` and the attribution limit stated (decision: Ransom, 2026-10-23).

### Configuration

```python
# src/inspect_swarm/_channel/filesystem_audit.py
DEFAULT_EXCLUDE = (
    ".git", ".hg", ".svn", "__pycache__", ".venv", "node_modules", ".lake",
    ".cache", ".mypy_cache", ".pytest_cache", ".ruff_cache", ".tox",
)

@swarm_channel
def filesystem_audit(
    paths: Sequence[str] | None = None,       # directories to watch; None: each watched sandbox's working directory
    exclude: Sequence[str] = DEFAULT_EXCLUDE, # file and directory names skipped at any depth
    interval: float = 1.0,                    # seconds between scans in the sandbox
    max_file_bytes: int = 32_000,             # largest text file whose content or diff is recorded
    max_bytes: int = 1_000_000,               # content and diff bytes recorded per member over the run
    max_events: int = 1_000,                  # change events recorded per member over the run
) -> Channel: ...
```

- **Names.** Registered as `inspect_swarm/filesystem_audit`, so `channels=["filesystem", "filesystem_audit"]` and `-T channels=filesystem,filesystem_audit` resolve it with its defaults ([swarm-api.md Resolving names](swarm-api.md#resolving-names)). The returned channel has `name=None` and `prefix=None` (it makes no records), adds no instructions (`instructions()` returns `None`) and opens no `ChannelState`. It is therefore accepted beside bridged members, whose CLIs' writes are among the changes nothing records today.
- **Logging and identity.** Every parameter is a plain value; `paths` and `exclude` come back from a log as lists and are accepted as any sequence. An arm with the channel and one without differ in `channels=`, so their eval-set identifiers differ, which is right: the watcher is a process members can see ([Security](#security)).
- **Validation** when `filesystem_audit()` is called raises `ValueError` naming the parameter: a path that is not absolute, is not in normal form (`posixpath.normpath(p) != p`, or begins with `//`, which `normpath` keeps and Linux reads as `/`), contains a NUL or a newline, is `/`, or is under `/proc`, `/sys` or `/dev`; two paths one of which contains the other; an `exclude` name that is empty, `.` or `..`, or contains `/` or a NUL; `interval` outside 0.2 to 60; `max_file_bytes` outside 0 to 1,000,000 (0 records no content); `max_bytes` outside 0 to 100,000,000; `max_events` outside 1 to 1,000,000.
- **Why the caps are per member.** A shared sandbox has one watcher for every member's work, so its allowances are the members' together: a watcher's caps are `max_bytes` and `max_events` times the number of members it covers (one for a member's own sandbox; all of them for a shared sandbox or a shared volume). With the defaults, content and diffs are capped at 1 MB and change events at 1,000 per covered member and watcher; serialized log size also includes paths, symlink targets, escaping and event metadata.
- **Why `paths` defaults to the working directory.** In the per-member shape the members' work is where their commands start (`/workspace` in `examples/proof_swarm.yaml`), and the whole filesystem is too broad (package installs, caches). A shared sandbox started in `/`, as `examples/compose.yaml` is, is refused at start with the fix ("filesystem_audit(): sandbox 'default' starts commands in /, the whole filesystem; give the directories to watch with filesystem_audit(paths=[...]), such as the filesystem channel's /shared and /scratch"). The channel does not copy the `filesystem` channel's paths: two channels' configurations stay independent, and a task states what it audits.

### Which sandboxes are watched

`SwarmRun` gives the audit's service ([Channel changes](#changes-to-channel-and-the-runtime)) each member's own sandbox name (`member_sandbox()`, `None` when it shares the caller's default) and the `filesystem` channel's `shared` path when that channel has `shared_volume=True`.

- **Per-member sandboxes.** One watcher in each member's environment, looked up by name in the sample's environments (as `_member.py` does). Its roots are `paths`, or that environment's working directory. When a shared volume is declared, every member's watcher skips the volume's path wherever it meets it, and one more watcher, covering every member, watches the volume from the first member's sandbox in roster order. A root equal to or inside the volume's path is refused at start, since its changes would be reported by every member's watcher. The `visible_sandboxes` services are not watched.
- **One shared sandbox.** One watcher, covering every member, in the environment members' `sandbox()` returns: the current default of the context the swarm runs in, which is the sample's default for a swarm at the root and an enclosing member's own sandbox for a swarm nested in a member that has one (`_member_sandboxes()` makes it the default, `src/inspect_swarm/_member.py:367-387`). That environment's actual name in this context (`default` at the root, `work` inside a member with `sandbox="work"`) is what the watcher's events carry as `sandbox` and `watcher` and what `fs_incomplete` lists.
- **Refused at start**, before any member, with `RuntimeError` naming the sandbox: the `local` sandbox (its commands run on the host); a sandbox without `python3` 3.8 or later on a system `PATH`; a resolved root that breaks a rule `paths` is held to at validation (not absolute, not in normal form or beginning with `//`, holding a NUL or newline, `/`, or under `/proc`, `/sys` or `/dev`), whether it is a working directory the probe reports or a declared shared volume's `shared` path, which the `filesystem` channel accepts more freely (it requires only an absolute path, so `/proc` and `/shared/../proc` pass it) and keeps accepting, the error naming the sandbox and the root; a watched root inside a declared shared volume; a root whose path, as far as it exists, has a symlink component (the watcher refuses it at its baseline, naming the component, so the fix is to give the real path); and a sandbox whose startup (probe, launch and baseline together) does not finish within the startup limit of 120 seconds, or whose watcher exits first (with its stderr, at most 4 KB) ([The service on the host](#the-service-on-the-host), invariant 1). A run configured with the audit never runs without it.
- **A volume mounted without being declared** (a compose file that mounts one volume in every member's service while the swarm has no `filesystem(shared_volume=True)`) is reported once per member's watcher, labelled with each. The swarm cannot see mounts it was not told about; the channel's docstring says to declare the volume.

### The watcher

One program using only the standard library, `src/inspect_swarm/_channel/_fs_watcher.py`, held to Python 3.8 ([Providers and images](#providers-and-images)). It is an importable module whose functions the tests call directly, and it runs only under `if __name__ == "__main__"`.

**Launch and user.** At start the service runs one probe, `exec_remote(["/bin/sh", "-c", PROBE], stream=False)` with no `user`, so that every sandbox call the audit makes goes through an `ExecRemoteProcess` and is covered by the guarantees of [What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote). It reports the working directory (`pwd`, the default root), the uid it runs as (`id -u`), the absolute path of `python3` resolved with `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, and, from that interpreter run as `python3 -I -B`, its version and the sandbox's `time.time()`. The clock offset is the sandbox's time minus the midpoint of the host's wall clock around the call, with half the round trip as its error; the bracket includes first-use setup (the tools injection) and transport time as well as the probe, so the error can exceed a poll interval, and the time bounds are widened by whatever it is, so they stay correct. It then starts `exec_remote([python3, "-I", "-B", "-c", BOOT], ExecRemoteStreamingOptions(input=..., stdin_open=True))`, also with no `user`, where `BOOT` reads the watcher's configuration and program from stdin and runs it, so neither appears in a command line; the process list shows `python3 -I -B -c "import sys,json;..."`. Probe and watcher both run as the sandbox's default user ([Current behaviour](#running-a-long-lived-process-in-a-sandbox)), the user members' commands run as unless a tool names another, so the watcher can read what members' commands can and no more; in the examples' images that is root.

**What it guards against.** Members' work goes on under the watcher while it scans: they create, rewrite, rename and delete files and directories, swap a directory for a symlink, keep Python files in their working directory and set environment variables. None of that may make the watcher read outside what it audits, record a change that did not happen or a deletion it did not see, or stop. A member with root who sets out to blind or forge the audit is out of scope; the record shows what it can of that ([Security](#security)). The watcher holds these invariants. How it meets each (the system calls, the output's encoding, the handling of each error) is the implementation's, and its tests demonstrate each one ([Testing](#testing)):

1. **It reads only the watched roots.** No symlink is ever followed, at a root, in an ancestor or at the final component, whatever a member renames or swaps during a scan, so nothing outside the roots, under an excluded name or on a skip path is read or recorded. A symlink is recorded by its target string only. FIFOs, sockets and devices are never opened, and none can block a scan. A root whose path, as far as it exists, has a symlink component at the baseline is refused, naming the component; a root a member later removes or replaces with a symlink or a file counts as empty, so its files are reported deleted.
2. **Its interpreter is isolated from the project and the environment.** The probe and the watcher run as `python3 -I -B`. `-I` puts neither the working directory (a member's project, `/workspace` in `examples/proof_swarm.yaml`) nor `PYTHONPATH` on the import path and ignores the user's site-packages and every `PYTHON*` variable, so a project's `json.py`, `hashlib.py` or `difflib.py` cannot replace the standard library's; it keeps the working directory, so the default root is unchanged. `-B` is invariant 3's.
3. **It writes nothing into the sandbox.** The watcher only lists, stats and reads, and neither it nor the probe's interpreter step writes a bytecode cache for the modules it imports (`-B`, which `-I` alone does not imply, since `-I` ignores `PYTHONDONTWRITEBYTECODE`); its one output is its stdout, which only the handle that started it reads. So a watcher the host has lost track of (a kill whose request failed, a start whose response never came) changes no file and no record: it costs CPU, and appears in the process list, until the sandbox is cleaned up at the sample's end.
4. **A race is one path's, never the watcher's.** Any failure while observing one path (it went away, changed type, or changed while being read) is that path's: the path is left for the next scan, keeping its previous entry and its bounds, and is reported with `omitted: "in_flux"` and no hash after ten scans in a row. Only a permission error records it as `unreadable`. Only an error outside the work on one path (writing stdout, the snapshot limit of invariant 8, a bug) ends the watcher.
5. **A deletion is reported only when a scan established it.** A path in the previous snapshot is *gone* when the nearest of its ancestors the scan reached was listed completely ([Scans](#the-watcher)) and the path was not found. Below a directory not listed completely, the previous entries are carried unchanged with their old `seen`, so an unreadable directory or a truncated scan reports no deletion and no new file. A directory that disappears or stops being a directory during a scan is settled in that scan: the files it held are not found.
6. **The final scan defers nothing, and what it cannot settle makes the audit incomplete.** It has no next scan, so every change it detects is in the record: a path it cannot read consistently is a `wrote` with `omitted: "in_flux"` and no hash, and one that went away is not found. Any path the final scan could not settle, whatever it is (an existing file still changing, a file pending since an earlier scan, a new one, a directory), is counted in `unsettled`, and the audit is complete only when that count is zero.
7. **Every line the host accepts arrived whole.** Each output line carries `n`, its number, consecutive from 0 for `ready`, and the SHA-256 of its own text. The host uses nothing from a line whose hash does not match, skips a line whose `n` it has already accepted, and records a gap for every `n` it never accepted; each line it could not accept makes the watcher's audit incomplete ([Host-side loss](#the-service-on-the-host)). The hash guards against the transport, not a member, who can compute it too.
8. **Its resources are bounded.** Hashing stops at 64 MiB per file, a scan at 200,000 entries, the held texts at 64 MiB in total, and the snapshot it keeps between scans (every file, symlink, directory and pending path, those carried below a directory it could not list included) at 400,000 entries, twice a scan's, so that a full scan and the entries it carries both fit. A scan that would take the snapshot past that limit ends the watcher with an error naming the limit, which the host records as `audit_lost` (`exited`, with that stderr), so the sandbox's audit ends there, not complete; the watcher never drops entries to stay within it, which would forget what it covers or report deletions it did not see; the caps bound its output, and output the host has not read blocks the watcher rather than growing its memory.

**Scans.** The first scan is the baseline; it reports nothing, holds no content and computes no hashes, so its cost is a listing and a `stat` per entry, however large the files. Every `interval` seconds after it the watcher scans each root, skipping `exclude` names and the skip paths and walking directories without reporting them. A scan's start time is taken before its first observation and its end time after its last. Its snapshot holds, for each regular file and symlink, its signature (device, inode, size, `st_mtime_ns`, `st_ctime_ns`) and `seen`, the start time of the scan that observed that signature; and for each directory it has met, `listed`, the start time of the last scan that listed it completely, or none. A directory is *listed completely* when the scan read every entry without error and within the limit; one it could not open or finish (a permission or I/O error, too many open files, or the entry limit, which also marks the scan truncated) is not. A root that does not exist counts as an empty directory listed completely, so a directory members create later is picked up.

**Changes.** Each scan after the baseline compares with the previous snapshot:

- a gone path whose file appears at a path new in this scan with the same device, inode, file type, size and `st_mtime_ns`, none of which a rename changes: a move, and the watcher reads the new path. When the old entry's hash and the new one are both known (for a symlink, both targets), they decide: equal is `renamed` (`old_path`, `path`), different is a `deleted` and a `wrote` with `new: true`. When either is not known (a baseline file never written since, whose hash the baseline did not compute, or a hash omitted as too large, unreadable or in flux), those fields do not prove the content unchanged, since rewriting a file in place at the same length and restoring its modification time keeps them all; it is then a `renamed` followed by a `wrote` (`new: false`) on the new path, recording its content as a first write does, under the usual caps. A rename is inferred, never observed: two snapshots cannot tell a move from a deletion followed by an unrelated creation, and Linux filesystems reuse a freed inode at once, so the same device and inode alone prove nothing. A match on device and inode with anything else changed is therefore a `deleted` and a `wrote` with `new: true`, never a rename, which is also how a file renamed and modified in one interval is recorded. An inode that appears at a new path while its old path is carried is a `wrote`, not a rename;
- a path that is new and not a rename's target: `wrote`, `new: true`;
- a path whose signature changed: read it. No event only when the inode is unchanged and an available hash proves the content unchanged (the previous and the current hash are both known and equal; for a symlink, the same target), as after `touch` or `chmod`. Otherwise `wrote`, `new: false`, with `replaced: true` when the inode changed (an editor's or `sed -i`'s write-and-rename). A changed file with no hash on either side (over 64 MiB, unreadable, in flux) is therefore always a `wrote`, with `sha256: null` and `omitted` saying why;
- a gone path that was not renamed: `deleted`.

Events of one scan are written renames first, then writes, then deletions, each sorted by path.

**Time bounds.** A scan is not atomic, so each change carries its own bounds, in the sandbox's clock: the change happened in `(after, time]`. `time` is the end of the scan that observed the new state. `after` is the start of the scan that last observed the earlier state, which is no later than that observation: for a `wrote` on an existing path and for a `deleted`, the previous entry's `seen`; for a `renamed`, the old path's `seen`; for a new path, the `listed` time, in the previous snapshot, of its nearest ancestor directory there, the last complete listing that showed the path absent, or `null` when that directory was never listed completely (the file may predate the audit). A path left for a later scan keeps its bound: an existing path keeps its previous entry, and a new one is held as pending with the `after` computed when it was first found. A long scan widens the bounds; it never makes them wrong.

**What a write records.** The watcher reads a regular file only while it is still the file the scan listed, hashes the whole file with SHA-256 up to 64 MiB (a larger file has `sha256: null` and `omitted: "size"`) and keeps its first `max_file_bytes + 1` bytes; a file that changed while it was read is left for the next scan (invariant 4). The content is text when the bytes decode as UTF-8, hold no NUL and number at most `max_file_bytes`. For each path the watcher holds the text of the last version the audit recorded, with its hash: one written in full or as a diff, so a version the log alone can rebuild. It holds nothing after the baseline. For a text write it records one of:

- `diff`, with `base_sha256`: a unified diff (`difflib.unified_diff`, three lines of context) against the held text, when it holds one, both the held and the new text are empty or end with a newline, and the diff is shorter than the content. `difflib` writes no marker for a last line without a newline, so a diff across such a line could not rebuild the file exactly; that case records `content`;
- `content`: the whole new text otherwise, which makes a path's first recorded version after the baseline its full content, unless a rename carried the held text to it (below).

Anything else records no content, with `omitted`: `"binary"`, `"size"`, `"unreadable"`, `"budget"` (the watcher's `max_bytes` allowance is spent; size and hash are still recorded) or `"in_flux"`. A write that records neither content nor a diff drops the path's held text, so its next text write records full content again; eviction from the held texts, oldest first, has the same effect. A rename moves the held text to the new path; a deletion drops it. Every diff's base is therefore the last version the audit recorded for that path, and `base_sha256` names it. A symlink records its `target` (at most 4,096 bytes before encoding), encoded as paths are (below).

**Paths as text.** Every recorded path (`path`, `old_path`) and symlink `target` is its bytes decoded as UTF-8 with each backslash doubled and each byte that does not decode written as `\xNN`, and `lossy: true` says one of them had such a byte. Because every literal backslash is doubled, a `\x` in the text only ever stands for a raw byte, so the text and the bytes determine each other: two different files never share a recorded path, and the metrics count distinct files by that text. A name with a backslash, rare on Linux, reads with it doubled.

**Caps.** The watcher keeps its own count against its allowances. Once `max_events` events are written it writes no more change events but keeps scanning, so its snapshot stays current, and counts what it would have written by kind. Content and diff bytes count against `max_bytes`. The service applies the same allowances again to what it records, so a watcher that writes more is cut off at the host too.

**Output and pacing.** One JSON object per line, ASCII only, flushed after each scan: `ready` (baseline time and counts of files and unreadable directories, truncated), the change events, `done` (counts by kind, dropped counts, truncated scans, the count of paths the final scan left `unsettled`), each a count, never a list, so no line grows with the tree, each with its `n` and hash (invariant 7). Change events are bounded by the caps, and the host reads up to 1 MiB a poll and polls again at once while output keeps coming, so output is read within about one poll interval of being written. If the host falls behind, the tools server's buffer fills and the watcher's write blocks; scans pause and the next scan reports what changed in the longer interval, with bounds that cover it.

**Ending.** The watcher waits for the next scan on stdin. End of input means stop: it runs a final scan (invariant 6), writes its events and `done`, and exits 0. An error outside the work on one path writes a traceback to stderr and exits 1.

### The service on the host

`FilesystemAuditService`, opened per run by `filesystem_audit()`'s `service()`, runs in [the run order](#the-run-order):

- **`start(tg, swarm_start)`** probes and launches every watched sandbox concurrently, waits for each `ready`, writes one `audit_started` per watcher as it becomes ready, and starts one poller per watcher. It raises `RuntimeError` for every refusal of [Which sandboxes are watched](#which-sandboxes-are-watched), before the controller runs, so no member starts.
- **The poller** reads its watcher's output as lines, checks each (Host-side loss, below), converts its times to swarm time (sandbox time minus the clock offset, mapped from the host's wall clock to `anyio.current_time()` at start, minus the swarm's start), widens `after` down and `time` up by the clock error, applies the watcher's allowances again, so a watcher that writes more is cut off at the host too, and writes the evidence.
- **`stop()`**, after the final step, closes the stdin of each watcher still running, so it runs its final scan, waits up to 30 seconds in all for each watcher's `done`, and writes one `audit_ended` per watcher whose `audit_started` was written, from what its poller had accepted. A watcher that did not finish its final scan has `final_scan: false` and is not complete.

**Invariants.** The service holds these whatever the sandboxes and the run do. How it meets each (its tasks, cancellation and buffering) is the implementation's, and its tests demonstrate each one ([Testing](#testing)):

1. **Startup is bounded.** Each watched sandbox's whole startup, the probe included, then the launch and the wait for `ready`, has one finite deadline: the startup limit of 120 seconds from `start()`'s call, or the time cap's deadline when that is earlier ([Changes to `Channel` and the runtime](#changes-to-channel-and-the-runtime), item 5). Nothing the SDK does extends it (its awaitable mode has no timeout of its own). Missing the startup limit is a refusal naming the sandbox. A refusal or cancellation reaches the caller of `run()` as the original exception, and `stop()` still runs; a `start()` that did not complete has started no poller.
2. **Sandbox calls run only in `tg`.** Every call on a sandbox or a handle (the probe, the launch, the polls, `close_stdin()`, `kill()`) and its clean-up runs in a task in `tg` that catches every exception, so nothing the service does after `start()` ends the swarm, and `start()` and `stop()` wait only for watchers to report, never for a sandbox call to return or clean up. A watcher whose exit was not seen is killed by that clean-up when the runtime joins `tg`, within inspect_ai's cleanup bound ([What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote)).
3. **Nothing is recorded after `audit_ended`.** The service closes a watcher's record before it writes that watcher's `audit_ended`: no `fs` event, `audit_error` or `audit_lost` and no counter change follows it, on a normal stop, after a failed start and on cancellation, even for output a poller had already received. So each `audit_ended` summarises the whole of its watcher's record, and the metrics, written after the join, count exactly what the ending records summarise.
4. **Everything the host holds or emits is capped.** Per watcher: change events by `max_events`, content and diffs by `max_bytes`, the partial line it buffers by the longest line a valid watcher can write (its content at `max_file_bytes`, its paths and target with their escaping, and its metadata), and its diagnostics by a fixed number of `audit_error` events and 4 KB of stderr. Whatever goes past a cap is counted, not held or written: an overlong line is a `corrupt` line, and diagnostics past their limit are `suppressed`, both in `host_loss`, which makes the audit incomplete (`complete: false`).
5. **The audit's transport writes nothing raw to the transcript.** Through guarantees 1 and 2 of [What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote), what the watcher and the probe print, stdout and stderr, reaches the log only as the audit's validated and capped evidence and diagnostics, never as a `SandboxEvent`, before `audit_ended` or after it, and members' own sandbox events are unaffected.
6. **Errors leave `run()` unwrapped.** A refusal from `start()`, and whatever a member, the controller or the final step raises, leaves `run()` as the same exception, never wrapped in an `ExceptionGroup` by the services' task group ([the run order](#the-run-order), step 7).

**Host-side loss.** The poller checks each whole line before it uses anything in it, and counts per watcher, in `host_loss`, every line the watcher wrote that the log does not faithfully hold:

- a line whose hash does not match its text, that carries none (invariant 7 of [The watcher](#the-watcher)) or that is longer than the line cap is `corrupt`: recorded as `audit_error` (`reason: "corrupt"`) with its length, not its text, before its path, content or diff reaches the evidence. A chunk lost or repeated within a line, or across two, lands here;
- a verified line that does not validate against a pydantic model of the line types is `invalid`, recorded with its length;
- a verified line whose `n` is not above the last accepted one repeats output already read and is skipped silently; lines whose `n` was never accepted are `missing`, recorded as `audit_error` (`reason: "gap"`) with the number missing, which counts a corrupt or invalid line's `n` again.

Each is a loss of the record, not of the watcher, so the poller goes on, but the watcher's audit is no longer complete ([Evidence](#evidence)), however the run ends.

**A watcher lost.** If the process exits without having written `done`, before `stop()` or during its final scan (the snapshot limit, a crash), or polling fails after `exec_remote()`'s own retries, the poller writes `audit_lost` (time, `reason`: `exited` or `poll_failed`, exit code, stderr as data) and ends; after a poll failure the process may still run, so it is killed. No watcher is restarted (decision: Ransom, 2026-10-26): the sandbox's audit ends at the loss, its later changes are not reported, and its `audit_ended` names the loss in `lost` and is not complete, which puts the watcher in `fs_incomplete` ([Metrics](#metrics)). The other sandboxes' audits go on. A member that runs `pkill python3` therefore ends the audit of its sandbox, and the record says when. A watcher that neither exited nor answered within `stop()`'s wait is logged as a warning naming the sandbox, since its process may still run until clean-up.

### What the audit needs from `exec_remote()`

The probe and the watcher are the audit's only sandbox calls, and both go through `exec_remote()`. The audit needs these observable guarantees from it and from the sandbox proxy. They are owned by the inspect_ai prerequisites ([Implementation plan](#implementation-plan), steps 1 and 2), which specify, build and test them for every user of a long-lived handle; how inspect_ai meets them (suppression placement, serialization, acknowledgement, the iterator's queue) is theirs, not this design's (decision: Ransom, 2026-10-26 and 2026-10-29):

1. **Suppression is the caller's own.** A task that suppresses its sandbox events suppresses only its own: another task's command on the same sandbox, a member's, logs its `SandboxEvent` as usual.
2. **No audit call writes raw output to transcript events.** Every call the audit makes on a handle, the start, the polls, `close_stdin()`, `kill()`, the awaitable mode's iteration and the clean-up on cancellation included, can run without logging the process's output, so a `SandboxEvent` never carries the watcher's stdout or stderr.
3. **A normal stop delivers every record.** When no call fails, every byte the process writes to stdout, output `close_stdin()` returns included, reaches the iterator once and in order before the iteration ends, so a change the watcher reported just before its stdin closed is kept beside the `done` it writes after.
4. **Clean-up is bounded.** Every wait on a handle, `kill()` and a cancelled start or iteration included (the start's first-use tools injection and the awaitable mode's iteration are part of them), returns within a bound inspect_ai states, *the cleanup bound*; when clean-up returns, the process's exit may be unconfirmed.

Under these the audit is correct where they leave something open:

- **An unconfirmed exit.** A watcher writes nothing into the sandbox ([It writes nothing into the sandbox](#the-watcher)), so one the host has lost track of changes no file and no record, and its sandbox's audit is already recorded as lost or not complete. The service holds no locks or pid files in the sandbox and runs no clean-up command of its own.
- **Output when a call fails.** Guarantee 3 covers a normal stop only. When a call fails or a stop is cut short, a line damaged by a lost or repeated chunk fails its hash, a whole repeated line is skipped by its `n`, and a lost one is a recorded gap, each making the audit incomplete ([Host-side loss](#the-service-on-the-host)), so the record stays honest.

### Attribution by topology

- **A member's own sandbox.** A change in it has `member` set to that member: the change happened in member X's own sandbox during this run. It does not mean X wrote it (decision: Ransom, 2026-10-28). Most such changes are the member's own work: a tool call, a redirect, a script, a bridged CLI, a background process. Metrics count changes certainly after the member's end separately ([Metrics](#metrics)). The task's own setup before the swarm is in the baseline, not reported; a scorer's writes after the swarm come after the final scan.
- **Who else can write there.** Nothing in inspect_swarm reserves a member's sandbox: `_check_member_sandboxes()` keeps two members of one roster from sharing one (`src/inspect_swarm/_swarm.py:313-349`), and `_member_sandboxes()` selects the sample's existing environment without claiming it (`src/inspect_swarm/_member.py:367-387`). So these write into it too, and carry the member's label:
  - the run's controller, or a custom one, which runs in the caller's sandbox context and can reach every environment by name;
  - another swarm, running concurrently, nested in a member or called by a controller, or a later one in the same sample, whose members or shared default use the same environment;
  - processes the member started that outlive it, including into a later run;
  - anything outside a swarm run, such as a solver's own concurrent task.

  The audit does not distinguish these writers, and does not try to. `complete` and `fs_incomplete` are about observation loss, not about who wrote. An analysis that needs the writer takes it from elsewhere: the transcript's tool calls and sandbox events, set against each change's time bounds.
- **A shared sandbox or volume.** Changes have `member: null`. The writing process is not knowable from a scan, and no unprivileged kernel facility reports it ([Current behaviour](#what-ownership-says-under-users-isolation)). A change's bounds `(after, time]`, in swarm time, let analysis list the members with a tool call that overlapped them; that is a hint, since a background process of any member may have made it, and a change with `after: null` overlaps every call before `time`.
- **Users isolation is not a prerequisite, and would not be sufficient.** Under `users()` a file's owner is the member that created it, so the audit could attribute `wrote` events with `new: true` or `replaced: true` (a new inode, created by the writer) to the owner's member. It could not attribute writes into an existing file (`>`, `>>`, in-place editors, `text_editor`), deletions or renames, which are much of what members do to shared files. So `users()` does not unlock this channel; it would add attribution for one kind of change. It stays its own future item, built when an isolation experiment needs it ([swarm-implementation-plan.md Future work](swarm-implementation-plan.md#future-work)); attributing new and replaced files by owner under it is one step for then ([Not this design](#not-this-design)) (decision: Ransom, 2026-10-23).

### What the audit misses

Each run's records say which of these happened (`truncated`, `unreadable`, `dropped`, `omitted`, `audit_lost`, `audit_error`); the rest are properties of polling the design states here and the docs repeat:

- **Between scans.** Changes coalesce: several writes to a file in one interval are one `wrote` with the last version; a file created and removed within an interval is never seen; a file changed and changed back within an interval, to the same content and inode, shows no event. The default interval is one second.
- **Content.** Larger than `max_file_bytes`, binary, unreadable, past the budget, or still being written after ten scans or at the final scan: size and hash only (and no hash past 64 MiB, for an unreadable file or for one still being written). A diff is against the last version the watcher recorded, which may be several versions back when changes coalesced, and is in the log unless a line was lost (below).
- **Moves.** A `renamed` is inferred from an unchanged file at a new path, and when its content could not be compared (a baseline file never written since, or a hash omitted) it is followed by a `wrote` with the new path's content, so a move of such a file costs a write in the record and in `writes`; a file renamed and modified within one interval is a `deleted` and a new file, its version chain restarting with full content. A deletion followed by an unrelated creation that reused the inode is a move only if the new file also matches the old one's size, modification time (to the filesystem's timestamp granularity) and, when hashed, content, which the record cannot tell from a move.
- **Metadata-only changes to baseline files.** The baseline computes no hashes, so the first `touch`, `chmod` or same-content rewrite of a file unchanged since the baseline is a `wrote` (recording its content, as any first write does), counted in `writes`; after that, the watcher holds its hash and such a change gives no event.
- **What is not a file's content.** Directories, empty directories, permissions, owners, timestamps and extended attributes. Hard links are separate paths.
- **Where.** Outside the watched roots, under excluded names, on skip paths, below directories the watcher cannot list or a truncated scan did not reach, and in sandboxes not watched (shared services).
- **When.** Before the baseline; in a sandbox whose watcher was lost, everything after the loss; after the final scan; and the whole end of a run when the sample is cancelled.
- **Lines the host could not record.** A watcher line that arrived damaged, did not validate or never arrived is an `audit_error`, and the watcher's audit is not complete.
- **Diffs after a lost line.** The host records each verified diff as the watcher sent it and does not track the chain itself. When a line holding a path's content or diff is lost, the watcher has still advanced its held text, so the path's later diffs name a `base_sha256` the log does not hold, and none of them can be applied until a write recorded in full `content` (after an omission, an eviction, or a diff longer than the content) starts the chain again. The loss itself is already counted, so the audit is already incomplete; analysis finds the break by following `base_sha256` from each recorded version's hash.
- **Who.** In a shared sandbox or volume, no member is named; in a member's own sandbox, the member is the sandbox's, not a proven writer ([Attribution by topology](#attribution-by-topology)).
- **Time precision.** `(after, time]` spans from the start of the scan that last saw the old state to the end of the one that saw the new state, about two intervals for an ordinary change and more after a deferral; it is in the sandbox's clock, mapped to the host's by an offset measured once at start and widened by its error. Docker on Linux shares the host's clock; Docker Desktop runs containers in a VM whose clock can drift from the host's, as a Kubernetes node's can, and the offset is not measured again during a run.

### Reads

Reads are not tracked, and this design does not plan them as a later step. Polling cannot see a read (access times are not updated on `relatime` and `noatime` mounts), and inotify's open and access events say that a file was read, not by whom. In a member's own sandbox, its reads of its own files say nothing about communication; the reads that would, of a shared sandbox's or volume's files by another member, are exactly the ones that cannot be attributed without process-level tracing. The read side of the filesystem channel is what `read` evidence gives the shared-memory board ([swarm-memory-channel.md Evidence](swarm-memory-channel.md#evidence)); for files, only privileged tracing would.

### Providers and images

- **Docker** (Desktop and Linux): supported; the spike ran there. Each watcher costs the host `exec_remote()` polls, each a `docker compose exec` of the sandbox tools, plus the in-sandbox scan: one poll every 5 s while it is quiet, and while members are changing files usually two (the poll that returns a scan's output and an immediate one that finds none), more back to back when output backs up.
- **Kubernetes** (inspect_k8s_sandbox, gVisor by default): `exec_remote()` uses the same base implementation through `exec()`; scanning uses only `stat`, `open` and `read`, which gVisor implements. Not run here; a manual test is in [Testing](#testing). The clock offset matters there.
- **Other providers** work if `exec_remote()`'s tools injection works on them; a failure is a refusal at start.
- **`local`**: refused.
- **Images** need `python3` 3.8 or later on a system `PATH`; an image without it is refused at start with the requirement (decision: Ransom, 2026-10-23). Epoch's Lean image is to be checked when that port runs; a watcher built into inspect_ai's sandbox tools is the fallback if a real image lacks `python3` ([Alternatives](#alternatives-considered)).
- **Why 3.8 and not the package's 3.11.** inspect_swarm needs Python 3.11 on the host, where the swarm runs. The watcher runs on the sandbox image's own interpreter, never imports inspect_swarm or anything outside the standard library, and so needs only what its own code uses: `os.scandir`, `hashlib`, `difflib`, `json`, `select`. A 3.11 floor would refuse images based on Ubuntu 22.04 (3.10), Debian bullseye (3.9) and Ubuntu 20.04 (3.8) for nothing the watcher needs.
- **Keeping the floor real.** `_fs_watcher.py` is written to Python 3.8's syntax and standard library, with `from __future__ import annotations` so its annotations keep the repository's style. Three checks hold it there: ruff's `per-file-target-version` sets the file to `py38`, which rejects newer syntax such as `match`; a pyright execution environment whose `root` is the file sets `pythonVersion = "3.8"`, which also rejects runtime subscripts such as `list[str]()`; and a slow Docker test runs the watcher on `python:3.8-slim`, which catches standard-library functions newer than 3.8 that neither checker does (`str.removeprefix` passes both). *(Both configuration settings were checked against a scratch project with this repository's ruff and pyright.)*
- **No inotify**, so no watch limits, no per-directory watch races, and the same behaviour under gVisor and on volumes shared between containers ([Alternatives](#alternatives-considered)).

### Evidence

Each event is an `InfoEvent` with `source="inspect_swarm"`, `version: 1` and `type: "fs"`, written in the swarm's span. `run` is the run's id (`ChannelRun.run_id`, [Changes to `Channel` and the runtime](#changes-to-channel-and-the-runtime)), the one field that tells this swarm's stream from another swarm's in the same sample, which [Metrics](#metrics) relies on. `member` is the member whose own sandbox the change happened in, not a proven writer ([Attribution by topology](#attribution-by-topology)), or `null` in a shared sandbox or volume; `span_id` is `null`, because a change is the swarm's observation, not an act in a member's span (analysis joins a member to its span through its `member_result` event). Every event names its `sandbox` (the environment's name) and its `watcher`, the sandbox name, or `"<sandbox>:<volume path>"` for a shared volume's. Times are swarm time, as in member results.

| Kind | When | Fields beyond the common ones |
|---|---|---|
| `audit_started` | a watcher's baseline is ready | `scope` (`member`, `shared_sandbox`, `shared_volume`), `covers` (members), `paths`, `exclude`, `skip`, `missing` (roots absent at start), `interval`, `user` (the default user's uid), `files`, `unreadable`, `truncated`, `python`, `clock_offset`, `clock_error`, `max_bytes` and `max_events` for this watcher |
| `wrote` | a file or symlink was created or changed | `n`, `path`, `lossy`, `new`, `replaced`, `file_type` (`file`, `symlink`), `size`, `sha256`, one of `content`, `diff` (with `base_sha256`), `target`, `omitted`, `time`, `after` |
| `renamed` | a file or symlink was found at a new path with its identity unchanged and gone from its old one: inferred as a move, followed by a `wrote` when its content could not be compared ([Changes](#the-watcher)) | `n`, `old_path`, `path`, `lossy`, `file_type`, `size` (unchanged by the move), `sha256`, `time`, `after` |
| `deleted` | a file or symlink disappeared | `n`, `path`, `lossy`, `file_type`, `size` (from the last snapshot that held it), `sha256` (its last recorded hash, or `null`), `time`, `after` |
| `audit_lost` | a watcher stopped unasked; its sandbox's audit ends | `time`, `reason` (`exited`, `poll_failed`), `exit_code`, `stderr` |
| `audit_error` | a line from a watcher arrived damaged or did not validate, or lines never arrived | `time`, `reason` (`corrupt`, `invalid`, `gap`), `length` (for `corrupt` and `invalid`), `missing` (for `gap`) |
| `audit_ended` | `stop()` | `counts` by kind, `dropped` (`events` by kind, and `content`, the writes whose content was omitted as `budget`), `lost` (the time of its `audit_lost`, or `null`), `host_loss` (`corrupt`, `invalid` and `missing` lines, and `suppressed` diagnostics), `truncated_scans`, `unreadable`, `unsettled` (the number of paths the final scan could not settle), `final_scan` (whether it completed), `complete` |

`after` is a number or `null` ([Time bounds](#the-watcher)). `omitted` is one of `binary`, `size`, `unreadable`, `budget` and `in_flux`. Only `budget` is a cap dropping content: `max_file_bytes` decides which writes are eligible to record content at all, and an eligible text write the `max_bytes` allowance could not hold, at the watcher or the host, is counted in `dropped.content`. `binary`, `size`, a file that could not be read and a mid-run `in_flux` describe the file, not a loss: the change is in the record with its size and whatever hash it has, nothing is counted in `dropped`, and `complete` is unaffected; directories that could not be listed (`unreadable`) and paths the final scan could not settle (`unsettled`) are counted separately below. `complete` is true when the watcher was never lost, every count in `host_loss` is zero ([Host-side loss](#the-service-on-the-host)), no event was dropped and `dropped.content` is zero, no scan was truncated, no directory was unreadable, the final scan completed, and it left `unsettled` at zero. The host-loss counts are kept for the watcher's whole run, so a later valid `done` does not clear them. Content and diffs are JSON strings in the payload: data for analysis, never shown to a member. A path's recorded versions are rebuilt from a `content` and the `diff`s after it, each applied only to the version whose hash is its `base_sha256`. After a rename a path's first record can be a diff whose base was recorded under the old name, so analysis follows `renamed` events and `base_sha256` across names; a diff with no such version anywhere follows a lost line ([What the audit misses](#what-the-audit-misses)).

### Metrics

`EventLog` collects `fs` events beside `comm` events, each kept with its `run`, and `swarm_metrics()` counts only those whose `run` is this run's id, before grouping them by member or watcher. The interval's subscription also receives the `fs` events of any other swarm running in the sample meanwhile, nested or concurrent, whose shared audits have `member: null` and can name the same watcher (`default`), so neither the member nor the watcher tells the streams apart, and the span cannot either, since two runs can share one ([Current behaviour](#evidence-and-metrics)). The run id keeps each swarm's counts and validity to its own stream:

```python
class FsMetrics(BaseModel):
    writes: int = 0       # wrote events
    created: int = 0      # of them, new: true
    renames: int = 0
    deletes: int = 0
    files: int = 0        # distinct paths written, renamed from or to, or deleted
    after_end: int = 0    # events whose `after` is at or after the member's end (labelled with a member only)

class MemberMetrics(BaseModel):
    ...
    fs: FsMetrics | None = None           # changes in the member's own sandbox; None without filesystem_audit or in a shared sandbox

class SwarmMetrics(BaseModel):
    ...
    fs_unattributed: FsMetrics | None = None   # changes with no member: a shared sandbox or volume
    fs_incomplete: list[str] = []              # harness validity: watchers whose audit_ended is not complete
```

`after_end` uses the member's end time from `MemberTimes` and the event's lower bound, so it counts only what certainly happened in the member's sandbox after the member ended: typically what its leftover processes wrote, though any writer of [Attribution by topology](#attribution-by-topology) may have. A change whose bounds contain the end, or whose `after` is `null`, is not in `after_end`; the `wrote` events keep the member's label either way. `MemberMetrics.fs` counts changes in the member's own sandbox, with the same meaning. `fs_incomplete` is a harness-validity list like `never_acted`: an analysis of file traffic leaves those samples out or reports them.

### Changes to `Channel` and the runtime

The audit is the first channel that runs work beside the members for the whole run. It needs, all in this package:

1. **`Channel.service(run) -> ChannelService | None`**, returning `None` by default, beside `open()`; `filesystem_audit()`'s channel returns its service.
2. **`ChannelService`**, a protocol in `_channel/_channel.py`:

   ```python
   class ChannelService(Protocol):
       async def start(self, tg: TaskGroup, swarm_start: float) -> None:
           """Start, before any member starts; work that runs beside the members, and its clean-up, goes in `tg`. Raises to refuse the run."""

       async def stop(self) -> None:
           """Finish, after the final step: write the service's last evidence, leaving any clean-up to `tg`. Never raises, except to let the run's own cancellation propagate."""
   ```

   It is named for its lifecycle, work that runs beside the members, not for a judgment: the swarm's evidence and metrics component is already its Observer ([swarm-api.md Observer](swarm-api.md#observer)), and inspect_sentinel's monitors observe a step and return an `Observation` (decision: Ransom, 2026-10-23).
3. **`ChannelRun`** gains `run_id: str`, unique to the run (`uuid.uuid4().hex`, made by `SwarmRun`'s constructor, which runs once per swarm execution), `sandboxes: Mapping[str, str | None]` (each member's own sandbox, or `None`) and `shared_volume: str | None` (the `filesystem` channel's `shared` when it has `shared_volume=True`). The `Bus` keeps building the one `ChannelRun`, with `bus=self` as it does today: `SwarmRun` passes `run_id`, `sandboxes` and `shared_volume` into `Bus(...)`, the `Bus` builds the `ChannelRun` from them and its roster, calls each channel's `open()` with it and exposes it as `bus.run`, and `SwarmRun` passes that same object to each channel's `service()` (decision: Ransom, 2026-10-28).
4. **The run order.** `SwarmRun.run()` runs a swarm's services in [the run order](#the-run-order) below.
5. **The time cap is a deadline.** Services start inside the swarm's time, which `swarm_budget()` already counts, so the cap becomes an absolute deadline, `deadline = swarm start + cap`. `_time_cap()` sleeps until it (`anyio.sleep_until(deadline)`) instead of for the cap's length, so startup does not move the stop later. Services start under `anyio.CancelScope(deadline=deadline)`, which every AnyIO the package allows provides (`anyio.move_on_at()` is newer than its floor). If the deadline passes before every service is ready, `run()` stops the swarm with `swarm_time` and never enters the members' task group, so no controller runs and no member starts; the run then goes on in [the run order](#the-run-order), and the final step runs with every member `pending`. With or without a time cap, startup is bounded ([The service on the host](#the-service-on-the-host), invariant 1).

This minimal additive extension of the public `Channel` and `ChannelRun` is approved (decision: Ransom, 2026-10-23). The bus is unchanged: the audit makes no records, so `deliver()`, storm controls, notices and the bridged-member refusal do not apply to it.

#### The run order

`SwarmRun.run()` runs a swarm with services in this order, and the rest of this design refers to it rather than restating it (decision: Ransom, 2026-10-28):

1. **Start.** Once the swarm's start and span are set, `run()` opens a task group for services and, inside it, enters the guarded `try` of steps 4 and 7 before the first `start()` call; it then starts each service in the group, under the time cap's deadline (item 5), before the controller runs.
2. **Members.** The caps, the members' task group, the grace and the hard stop, unchanged.
3. **Final step.** The answer and the final event, before any service is stopped, so nothing a service does can delay or cancel them.
4. **Stop the services.** Each service's `stop()`, in a `finally` that also runs when a service's `start()` raised or was cancelled, a member, the controller or the final step raised, or the run was cancelled; every service's `stop()` is called even when an earlier one re-raised the run's cancellation. The `fs` evidence is frozen there.
5. **Join.** `run()` cancels the services' task group and waits for the clean-up left in it. That clean-up may run past the swarm's time cap and the sample's limit; it is bounded only by inspect_ai's cleanup bound ([What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote)), not by a budget or reserve of its own, and the sample is not made to end exactly at its limit.
6. **Ledger and metrics last**, in a synchronous outer `finally` after the join (today's `finally`, `src/inspect_swarm/_controller/_control.py:453-523`, moved outside the services' task group). So `wall_clock` and the time `overshoot` include the drain and the clean-up, and the metrics count every `fs` event.
7. **The same exception leaves.** The services' task group never changes what leaves `run()`. Everything inside it, from the first `start()` call (steps 1 to 4), runs in a `try` that catches any `BaseException` inside the group, so AnyIO does not wrap it in an `ExceptionGroup`; after the join and the accounting, `run()` re-raises that same object, as it re-raises `error` today (`_control.py:524-525`), so a member's `RuntimeError`, a final step's `ValueError` and `start()`'s refusal leave bare (`tests/test_background_members.py:249` matches one), and an error that was already a group stays that group. The services' own tasks catch their exceptions ([The service on the host](#the-service-on-the-host)), so the only other thing the join can raise is a cancellation that arrives during it; when nothing was caught, that cancellation is what leaves, and when something was, the caught exception leaves instead.

**Accounting.** The outer `finally` is given the exception leaving `run()` (step 7's, or `None`). `ended_by` is `None` when nothing is leaving, and otherwise `_exhaustion()` of that exception, which names a sample limit or an operator interrupt that arrived at any point, the drain and the clean-up included. Today it is `None if ended else _exhaustion(error)` (`_control.py:478`); `_exhaustion(None)` is not `None` (`_control.py:701-718`), so the test is whether an exception is leaving, not whether the final step ran. A final step that completed is never marked cancelled: a cancellation after it sets `ended_by` only, not `interrupted` or `final_cancelled`, whose meaning ("before or during its final step") is unchanged.

## Alternatives considered

**inotify, with polling where it is unavailable.** The issue's first suggestion. It gives exact times and sees short-lived files, but not the writer either, so it adds nothing to attribution. It needs a watch per directory, with a race for every new directory (files created before its watch is added are missed, so a rescan is needed anyway), it is bounded by `max_user_watches` on large trees, under gVisor it misses changes made outside the sandbox's kernel (a volume shared between pods), and between Docker containers it reports a shared volume's changes to every container's watcher. Polling at one second covers the changes the issue names, whose results persist, with one code path on every provider. inotify could later trigger an immediate scan inside the same watcher, with the same events, if an experiment needs sharper times.

**Scans driven from the host** (`find -printf` through `exec()` each tick, diffed on the host, changed files read with `read_file()`). No process in the sandbox to lose. Rejected: every tick is a host exec (a `docker compose exec` each) per sandbox, so timing is bounded by exec cost; each changed file is another exec or copy; and the execs either log a `SandboxEvent` each or call the unwrapped environment through private state. The watcher keeps the per-tick work in the sandbox and costs the host one poll per 5 s while quiet, a few more while files change.

**Scans at turn boundaries or around tool calls.** Would tie each change to a tool call. Rejected: bridged members have no turn boundary the swarm sees, background processes write between turns, not every member wires `swarm_on_continue()`, and in a shared sandbox it still cannot say which member's call it was.

**Process-level tracing** (fanotify reporting the writer's pid, the audit subsystem, eBPF). The only way to attribute writes and reads in a shared sandbox. Rejected: each needs `CAP_SYS_ADMIN`, `CAP_AUDIT_CONTROL` or BPF privileges that default containers and gVisor do not give, and granting them to a container running untrusted code as root weakens the sandbox's own boundary ([swarm-sandbox-isolation.md Survey](swarm-sandbox-isolation.md#survey-linux-isolation-inside-one-sandbox)).

**A watcher in inspect_ai's sandbox tools**, the binary `exec_remote()` already injects. No `python3` requirement, so any image works. Rejected for now: an inspect_ai feature and a rebuilt tools artifact, for an image we have not seen fail. It is the fallback if a real user's image lacks `python3`.

**The watcher as root.** `exec_remote(user="root")` would let it read files members' default user cannot. Rejected: it would read what members' commands cannot, so the log could hold content no member could have seen; not every provider can switch user (Kubernetes runs as the pod's user); and in today's images the default user is root anyway.

**Changes as bus records.** Rejected: `deliver()` is for what a member's tool call sends, needs a member's context, and applies storm controls and notices that make no sense for an observation; and a channel with records refuses bridged members, whose writes the audit is most needed for.

**An `audit=` argument on `swarm()`, or always on.** swarm-api.md gives the observer no argument because what it records is the same in every arm ([Observer](swarm-api.md#observer)). The audit is not free: a process members can see, sandbox CPU, a `python3` requirement and log volume. So it is opt-in, and as a channel it gets registration, logging, `-T channels=` and a distinct arm identity with no new mechanism.

**Working around `exec_remote()` on the host.** The audit could keep the API as it is and make up for it: an exclusive lock and pid file per watcher in the sandbox, so a second watcher signals the first before scanning; a clean-up command at the end that takes every lock and reports the watchers it could not stop; one task per handle, with the watcher writing heartbeat lines so that task wakes to close stdin; and launch fences so that a start cancelled in flight cannot scan later. Rejected: each piece works around one missing guarantee of the handle, together they are most of the service, and every other user of a long-lived handle keeps the gaps. Bounding the handle's waits in inspect_ai is smaller and bounds every caller's.

**Specifying the `exec_remote()` contract here.** This design could state the handle's whole lifecycle contract (each provider's queues, teardown budgets, how output is acknowledged) with inspect_ai's tests. Rejected: it is inspect_ai's API, its other users (the agent bridge, inspect_swe's agents) have their own needs of it, and the audit needs only the observable guarantees it lists; they are specified in inspect_ai (decision: Ransom, 2026-10-26 and 2026-10-29).

**Restarting a lost watcher**, with a new baseline, so a member's `pkill python3` costs only the changes of a gap. Rejected for the first version: a replacement can start while its predecessor still runs, so two watchers would scan one sandbox unless something in the sandbox stops the first, which is the machinery above. Without restarts a lost watcher's sandbox records nothing more, the loss is in the record, and the sample is in `fs_incomplete`; restarts are left for when a run shows losses matter ([Not this design](#not-this-design)).

**Default `paths` from the `filesystem` channel's directories.** Would make `channels=["filesystem", "filesystem_audit"]` work in a shared sandbox with no arguments. Rejected: it couples two channels' configurations, and the per-member shape has no such channel; a refusal with the fix at start is clearer.

**Full content on every write, no diffs.** Simpler analysis. Rejected for log volume: a 30 KB file edited a hundred times would log 3 MB; a diff records what changed. **Diffs against the baseline's text**, without recording it, would save the first full copy of each file, but the log could not rebuild what the file holds; the first recorded version is full content instead.

## Compatibility and migration

- **inspect_ai:** two prerequisites ([Implementation plan](#implementation-plan), steps 1 and 2).
  - Task-local suppression (guarantee 1): events that other tasks' commands log during a suppressed call were meant to be logged and now are, for the bridge's polls too.
  - The `ExecRemoteProcess` guarantees 2 to 4: their compatibility for the handle's other users is assessed with them in inspect_ai.
- **Ledger and metrics:** with a service, `wall_clock` and the time `overshoot` include the services' drain and clean-up, and `ended_by` can name a limit or interrupt that arrived after a completed final step, with `interrupted` and `final_cancelled` false ([the run order](#the-run-order)). Fields and their types are unchanged; a run without services is unaffected.
- **inspect_swarm API:** new `filesystem_audit()` and its registry name, `Channel.service()`, `ChannelService`, and three `ChannelRun` fields. Like everything in inspect_swarm, experimental ([swarm-implementation-plan.md Decisions](swarm-implementation-plan.md#decisions), item 6).
- **Eval logs:** only `InfoEvent`s, of a new evidence type `fs`, `version: 1`, and new optional metrics fields with defaults, so metrics written before them load. No schema or viewer change.
- **Existing swarms:** unchanged unless they list the channel. Listing it changes the arm's identity.
- **Tasks:** the audited sandboxes need `python3` 3.8+ and `exec_remote()` support; a shared sandbox starting in `/` needs `paths`. Each sample starts about one poll interval (5 s) later, counted against the swarm's time cap. After the final step, the drain (typically 5 to 10 s, at most 30 s) and the watchers' clean-up (within the cleanup bound) add to the sample's time, and may run past the swarm's cap and the sample's limit ([the run order](#the-run-order)); `wall_clock` counts them.

## Security

Untrusted input reaching the new code, and how it is handled:

- **File contents** (model output, possibly an injection relayed into a file): bounded by `max_file_bytes` and `max_bytes`, recorded only when valid UTF-8 without NUL, as JSON strings in `InfoEvent` payloads; never in a notice, a tool result, an instruction or any text a member sees. Binary content is never recorded.
- **File names** (any bytes but NUL and `/`): recorded as JSON strings in a reversible escaping, so a name cannot pass for another file's ([Paths as text](#the-watcher)), with `lossy` set when it had undecodable bytes; never interpolated into a command, a script or a harness-written line. The watcher's configuration comes from the eval author and reaches it as JSON on stdin.
- **Symlinks and special files.** No symlink is followed, at a root, in an ancestor or at the final component, so a member who swaps a directory for a symlink cannot make the watcher read, and the log record, content outside the watched roots or on a skip path under another member's name; only a symlink's target string is recorded. FIFOs, sockets and devices are never opened and cannot block a scan (invariant 1 of [The watcher](#the-watcher)).
- **Project files and Python settings.** The probe's interpreter step and the watcher run as `python3 -I -B`, so neither a module in the working directory (a member's project) nor `PYTHONPATH`, user site-packages or other `PYTHON*` variables can replace the standard library they import (invariant 2).
- **Size and shape bombs.** Hashing stops at 64 MiB, a scan at 200,000 entries, the held texts at 64 MiB; event and byte caps bound the output; output beyond the tools server's buffer blocks the watcher rather than growing memory. On the host, everything the service buffers or writes per watcher is capped, an overlong or newline-free stream and a flood of malformed lines included, and what goes past a cap is counted as loss (invariant 4 of [The service on the host](#the-service-on-the-host)).
- **What the watcher can read.** It runs as the sandbox's default user, the user members' commands run as by default, so it reads nothing their commands could not; a file or directory that user cannot read is recorded as unreadable. The eval author chooses `paths`; secrets the task keeps in the sandbox belong outside them.
- **Tampering.** A member with root in its sandbox sees the watcher in the process list and can kill it, flood a watched directory to exhaust the caps, make a directory unreadable, or write forged lines into the watcher's stdout through `/proc`. A loss is recorded and ends that sandbox's audit, marked incomplete; caps and unreadable directories are recorded; every line is schema-validated and capped again on the host, a damaged or malformed one is recorded by length only, a forged `n` that skips ahead is a recorded gap, and each of these leaves the watcher's audit incomplete. The label is by sandbox on the host, so a member can forge events only about its own sandbox (or, in shared topologies, unlabelled ones). The audit records what cooperative members did, and says when its record has gaps; it is not evidence against a member trying to hide.
- **Raw watcher output.** Every audit call on a sandbox runs with the service's task-local event suppression, so the watcher's and probe's output, a member's forged lines included, never reaches the transcript as a `SandboxEvent` outside the host's checks and caps (invariant 5 of [The service on the host](#the-service-on-the-host)).
- **The member's `SandboxEvent`s.** Without guarantee 1 of [What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote), the watcher's polls would drop some of the member's own sandbox events from the log ([Current behaviour](#running-a-long-lived-process-in-a-sandbox)); it is a prerequisite, not an option.
- **Isolation between samples:** each run's service holds its own watchers and counters; the `Channel` holds configuration only.

## Testing

Tests use mockllm with scripted tool calls and run on asyncio and trio; those marked `slow` need Docker and run only with `--runslow`, as `tests/conftest.py` arranges.

- **The watcher** (`tests/test_fs_watcher.py`, no Docker). It runs the module as a subprocess with the host's Python over a temporary directory, and calls its functions directly to change a file between two steps of observing it or to lower a limit. Table-driven, one group for each part of the record and each invariant ([The watcher](#the-watcher)), each case asserting the events and `done` that result:
  - *The record.* Each kind with its fields: create; append in place; overwrite; write-and-rename over a path (`replaced: true`); rename; a rename and a deletion of baseline files never written since, each carrying `file_type` and `size` (a symlink's `size` is its `lstat` size, the length of its target); a baseline file rewritten in place at the same length with its modification time restored (`os.utime`) and renamed before the next scan, recorded as a `renamed` and a `wrote` holding the changed bytes, beside an unchanged baseline file renamed (also a `renamed` and a `wrote`) and a file renamed after a recorded write, whose hash is known (a `renamed` alone); rename and modify in one interval (a `deleted` and a `wrote` with `new: true`); a deletion and an unrelated creation that reuses the old file's device and inode (the reuse arranged with a controlled snapshot), recorded as a `deleted` and a `wrote` with `new: true`, never a rename; a hard link's old name removed (a `renamed`); delete; a symlink (its target). `touch` with no content change gives no event on a file whose hash the watcher holds (after a recorded write) and a `wrote` on a baseline file not changed since, a changed file with no hash (a lowered hash limit) is always a `wrote`, and a file created and removed within one interval gives none. Excluded names at depth are skipped. The bounds contain the change, after a slow previous scan (a controlled clock), for a file in a new subdirectory (`after` from its parent's listing) and for a directory unreadable at the baseline (`after: null`).
  - *Rebuilding from the log.* The first write after the baseline records `content`, later ones a `diff` on the previous recorded hash, a write with content omitted is followed by full `content`, and a rename carries the chain; files that gain, lose or lack a final newline are rebuilt byte for byte. Names that differ only in raw bytes, including two a single-escaping rule would render alike, and a name with a literal backslash are recorded as distinct paths and each rebuilt to its bytes; a symlink whose target holds a byte that is not UTF-8 and one whose target holds a literal backslash record targets that validate as the line model and decode back to their bytes.
  - *Caps and omissions.* Binary, over `max_file_bytes`, unreadable and past `max_bytes`, each with size and hash as the record says; `max_events` reached, with the dropped counts in `done`. Table-driven, each reason alone in an otherwise clean run: `budget` counts in `dropped.content` and makes the audit not complete; `binary`, `size`, an unreadable file and a mid-run `in_flux` count nothing in `dropped` and leave it complete; an unreadable directory and a final-scan `unsettled` each make it not complete through their own counts.
  - *Invariant 1, the roots only.* With a file of known content outside the root: a subdirectory, an ancestor of a file being read and a root each replaced by a symlink to the outside directory at each step of a scan, and a symlink in a member's root pointing into a skip path. The outside content is never read or recorded, the symlink itself is a `wrote` with its `target`, and the replaced root reports its files `deleted`. A FIFO never blocks a scan, and a root with a symlink component at the baseline makes the watcher exit with an error naming it.
  - *Invariant 2, isolation.* Launched with the service's command line from a working directory holding `json.py`, `hashlib.py` and `difflib.py` that raise on import, and with `PYTHONPATH` naming another such `json.py`, the watcher reaches `ready`, records changes and reports the working directory unchanged; so does the probe's interpreter step. *Invariant 3, writing nothing.* A run of the probe's interpreter step and of the watcher through `ready`, changes and `done` leaves the temporary root and the working directory unchanged; the interpreter's own files are checked in the Docker test, in a disposable container, not here.
  - *Invariants 4 and 5, races and deletions.* At each step of observing a path, the path deleted, replaced by a symlink, by a file or by another inode, or changed: the watcher keeps running, reports nothing for the path in that scan, and the next scan reports its real state with bounds that contain the change; a path still changing after ten scans is `in_flux`. An unreadable directory and a truncated scan report no deletion below them. A directory removed or replaced by a file during a scan reports the files it held `deleted` in that scan.
  - *Invariant 6, the final scan.* The same changes made during the final scan each leave the path in the record, as `deleted` or as a `wrote` with `omitted: "in_flux"`, with `done` following; an existing file and a newly created one each still changing through the final scan, and a directory that changes type back and forth while the final scan settles it, are each counted in `unsettled` in `done`, and the audit's `audit_ended` is not complete.
  - *Invariant 7, the lines.* `n` is consecutive from `ready` through the change events to `done`, and every line's hash matches its text.
  - *Invariant 8, retained state.* With the snapshot limit lowered and `max_events` already reached, a directory made unreadable after the baseline while each later scan creates new files elsewhere: the snapshot never holds more entries than the limit; while it fits, the carried entries report no deletion; and the scan that would exceed it makes the watcher exit 1 with the limit named on stderr, having reported no deletion below the unreadable directory. In the channel tests, a stub watcher that exits that way is recorded as `audit_lost` (`exited`) and its `audit_ended` as not complete.
  - *Ending.* End of stdin gives a final scan, `done` and exit 0.
- **The service plumbing** (`tests/test_channel.py`, with a test channel whose service records calls): `start()` runs before any member's first model call and `stop()` after the final event, every member and background drain ended; `stop()` runs when a member or the final step raises and after a swarm stop's hard stop, and every service's `stop()` runs when the run is cancelled; a `start()` that raises fails the sample with no member started; a service's task never ends the swarm; a channel with a service and no records is accepted beside a bridged member; `ChannelRun.sandboxes` and `shared_volume` for each topology, a `run_id` that differs between two runs of one swarm, and `open()` and `service()` receiving the identical `ChannelRun`, whose `bus` is the run's bus.
- **The channel without Docker** (`tests/test_filesystem_audit.py`): `"filesystem_audit"` and `inspect_swarm/filesystem_audit` resolve with defaults, including from `-T channels=...`; the plan step logs its parameters and `create_registry_object()` rebuilds it, lists back to sequences; arms with and without it have distinct identifiers; each validation bound raises, including `//`, `//proc`, `//sys/x` and `//dev`. The rest use stub sandboxes whose `exec_remote()` runs the watcher locally over a temporary directory per environment, or a scripted stub handle where a test needs to control the stream:
  - *Topologies and labels.* Two per-member sandboxes, each labelled with its member; a controller's write into a member's sandbox (through `sandbox(<that member's sandbox>)`) recorded with that member's label, as documented; `member: null` for a shared sandbox; a shared swarm at the root watching `default`, and one nested in a member with `sandbox="work"` watching `work`, its events carrying `sandbox` and `watcher` `work` and an incomplete audit listing `work` in that run's `fs_incomplete`; a declared shared volume (one temporary directory both stubs expose at one path) reported once, unattributed, and skipped by the members' watchers.
  - *Refusals.* A root inside the volume; `local`, a missing `python3`, a working directory of `/` and one under `/proc`, and a declared shared volume at `/proc` and at `/shared/../proc`: each refused before any member starts with the sandbox and root named. Probe and watcher are started with no `user` and the interpreter as `python3 -I -B`.
  - *The record.* Times in swarm time with the measured offset, the bounds widened by its error; host-side caps applied to a watcher that ignores its own; two paths that differ only in raw bytes counted as two files; a normal `done` giving `final_scan: true` and a complete audit; a `done` with a nonzero `unsettled` giving that count and `complete: false`.
  - *Losses.* A watcher killed mid-run gives `audit_lost` (`exited`), no later events from that sandbox, `lost` and `complete: false` in its `audit_ended`, while another sandbox's audit goes on; one that exits during its final scan (the snapshot limit, lowered, or a crash) gives `audit_lost` (`exited`) with its exit code and stderr and `final_scan: false`; a poll that fails while the process is alive gives `audit_lost` (`poll_failed`), the handle killed and no second watcher; a watcher that never answers `stop()` is cut off after the wait (lowered), with `final_scan: false` and the warning. Host-side loss, each followed by the watcher's valid final scan and `done`: a chunk lost or repeated within a line or across two, in each field that reaches the evidence (`content`, `path`, `old_path`, `diff`), is `corrupt` with nothing from the line in the evidence; a schema-invalid line is `invalid` with its length and no text; a dropped line is a `gap` with the number missing; a chunk of lines yielded twice is recorded once; a quiet watcher stopped while a poll is in flight records its final scan's events once each. Each loss gives an `audit_ended` with that count in `host_loss`, `final_scan: true` and `complete: false`, and every other line of the stream recorded as usual. A dropped line holding a path's `content`, followed by that path's diffs and a write recorded in full, records the diffs as sent and the full `content` after them.
  - *Invariant 1, startup is bounded.* With a time cap, a probe that never answers is cancelled by the cap's deadline: `start()` returns at the deadline, the final step runs, and the join ends within the stub handle's cleanup bound with no stub watcher running. With no time cap and the startup limit lowered, a probe that keeps answering polls as running without finishing, and separately a watcher that never reports `ready`, are refused at the limit naming the sandbox, no member starts, `run()` raises that `RuntimeError` bare, and `stop()` runs. A `start()` failed by another sandbox's refusal, and one cancelled, after a first watcher was ready leave no poller running and record an `audit_ended` (`final_scan: false`, not complete) for the ready watcher and none for the other.
  - *Invariant 3, nothing after `audit_ended`.* A stub handle with a chunk of change lines queued, already received but not yet processed, when `stop()` closes the record, on a normal stop and on a cancelled sample: no `fs`, `audit_error` or `audit_lost` event of that watcher follows its `audit_ended`, and its counts equal the events before it and what the metrics count.
  - *Invariant 4, host caps.* A stream that never writes a newline keeps the host's buffer within the line cap and records one `corrupt` line per overlong line; many invalid lines after `max_events` is reached write no more `audit_error` events than their limit, the rest counted as `suppressed`; both audits end with `complete: false`.
  - *Invariant 5, no raw transport in the transcript.* With a stub handle whose responses to `close_stdin()` and `kill()` carry queued corrupt and over-budget stdout and a stderr marker, on a normal stop, a watcher killed after a poll failure, and a sample cancelled while a poll is held open: the whole sample transcript, not only its `fs` events, holds no `SandboxEvent` from the audit's calls and no copy of the marker or the queued bytes, while a member's concurrent `exec()` on the same sandbox keeps its `SandboxEvent`.
- **The run order** (`tests/test_channel.py`, step 4, with a self-contained test service whose `stop()` writes an evidence event and whose `tg` clean-up takes a controlled, shielded time): the final event comes before the service's `stop()` evidence, and the ledger and metrics after the join; `wall_clock` and the time `overshoot` include the clean-up; with a sample time limit and, separately, an operator interrupt arriving during the clean-up, the answer and the final event are kept, the cancellation arrives when due, the join returns once the clean-up ends, and the ledger has `ended_by` set with `interrupted` and `final_cancelled` false; a run that completes normally with the same slow clean-up has `ended_by` `None`. The service's invariant 6: with a service in the run, a `start()` refusal, a member's `RuntimeError` and a final step's `ValueError` each leave `run()` as the same bare exception, not an `ExceptionGroup`, and a member's error that was already a group leaves as that group. With the time cap: startup shorter than the cap, with an explicit `Budget(time=...)` and with a cap derived from the sample's time limit, stops the swarm at swarm start plus the cap, not later; startup longer than the cap stops it with `swarm_time` before any member starts, runs the final step and the service's `stop()`, and leaves every member `pending`. These tests also run once, before the step that adds them merges, in an environment uv resolves with `--resolution lowest-direct`, so on the oldest AnyIO the dependencies allow.
- **Metrics** (`tests/test_metrics.py`): `FsMetrics` per member from scripted `fs` events, `after_end` against the member's end time (a change whose bounds contain the end, and one with `after: null`, not counted), `fs_unattributed`, `fs_incomplete` (from an `audit_ended` with `complete: false`, whatever made it so, and, end to end through the channel's stub sandboxes, a lost watcher, a host-side loss and a nonzero `unsettled` each putting the watcher there), and metrics written before these fields loading. Other swarms' streams, with real swarms and the ledger's own transcript subscription in one sample, each run writing `fs` events whose payloads have `member: null`, `span_id: null` and `watcher: "default"`, one write each to different paths, with only one run's `audit_ended` incomplete: a member that runs an inner swarm through `run()`, a controller that calls an inner swarm directly, and two swarms called directly and concurrently under one span. In each, every run's `fs_unattributed` counts its own one write and one file, and only the incomplete run's `fs_incomplete` is `["default"]`.
- **Docker** (`tests/test_filesystem_audit.py`, `slow`): a shared sandbox with two `react()` members writing by redirect, by `python3 -c` and by a `nohup` background command, recorded with content and `member: null`; per-member sandboxes with a declared shared volume, each member's changes labelled with it and the volume's once and unlabelled; a member's `pkill python3`, which kills its watcher, recorded as `audit_lost` with that sandbox's audit incomplete and the other's going on; every member `bash()` call has its `SandboxEvent` while watchers poll, and no `SandboxEvent` in the sample carries a watcher's output (guarantees 1 and 2); a file written just before `stop()` closes a watcher's stdin, reported before the close, and the `done` written after it both recorded, the audit complete (guarantee 3); a sandbox on `python:3.8-slim`, which the probe accepts and whose watcher reports a write, a rename and a deletion, and in which, with the standard library's `__pycache__` directories of the modules they import removed first, the probe and the watcher create no file under the interpreter's prefix (invariant 3); a per-member sandbox whose `/workspace` holds a `json.py`, `hashlib.py` and `difflib.py` that raise on import and whose environment sets `PYTHONPATH` to a directory holding another, audited as usual from `/workspace`; an image without `python3` (`debian:bookworm-slim`) refused.
- **Kubernetes** (by hand, against a cluster with inspect_k8s_sandbox's default chart): the per-member Docker test with the k8s sandbox, to confirm `exec_remote()` and scanning under gVisor and to record the measured clock offset.
- **inspect_ai** (its own suite): each guarantee of [What the audit needs from `exec_remote()`](#what-the-audit-needs-from-exec_remote) is tested with the prerequisite that owns it, including a process that writes a line, has its stdin closed and writes a last line: both reach the iterator once, and no `SandboxEvent` carries either.

## Not this design

Noticed and left out, for Ransom to file if wanted:

- **`no_events()` drops other tasks' sandbox events today** (inspect_ai). Step 1 fixes it; it already affects every `sandbox_agent_bridge()` poll in a sandbox where other tools run, which a swarm's shared sandbox with a bridged member is.
- **A start retried after a timeout can start a second process** (inspect_ai), for its `ExecRemoteProcess` contract. The sandbox retries a timed-out request, `exec_remote_start` included, and a first attempt that started the process before timing out leaves that process running beside the retry's, unknown to the host. Harmless for the audit, whose watcher writes nothing into the sandbox, but not for a command with side effects. Fixing it needs the tools server to recognise a repeated start.
- **Restarting a lost watcher** ([Alternatives](#alternatives-considered)), if runs show that members end watchers often enough to matter.
- **Attributing new and replaced files by owner under users isolation**, once users isolation is built: map the owner's uid to its member for `wrote` events with `new` or `replaced`. Under it the watcher would also need its own identity, since members would no longer share the default user.
- **An analysis helper** that reads a sample's `fs` events as rows, rebuilds each path's recorded versions, and lists, for each unattributed change, the members whose tool calls overlapped its time bounds.
- **`fs` events in members' timelines.** They are in the swarm's span, so a member's timeline in the viewer does not show its file changes.
- **inotify as a trigger** for immediate scans inside the same watcher, for sharper times.
- **A final snapshot** of the watched trees (paths, sizes, hashes) at the swarm's end, for scorers and analysis that want the end state without replaying events.
