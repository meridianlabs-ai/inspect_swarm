# Inspect Swarm: operator intervention for every member

## Overview

An operator watching a running swarm reaches any member by its roster name from `inspect ctl sample agent`, on the control channel every eval runs on asyncio. `list` shows the swarm's members, what each is doing and which actions each takes now. `message` gives one member a message from the operator, at its next turn or, with `--interrupt`, now, cancelling what its turn is doing, a long tool call included. `pause` and `resume` hold one member, or with `--group` the whole swarm, at turn boundaries. `stop` ends one member, or stops the whole swarm the way its own stopping rules do, after which the sample goes on to its final answer and its scorers. Messages reach every native member (`react()` and `deepagent()`, with or without background work); pauses reach those without background work; bridged CLI members take only `stop`. On trio the control server does not start, so none of this is available there.

inspect_ai holds a small, generic registry: code running in a sample makes named agents, and named groups of them, addressable by the control channel, which lists them and sends them `message`, `pause`, `resume` and `stop`. The swarm registers itself as one group, with one agent per member, and runs every action in its own context. A message is an ordinary operator `UserMessage` posted to the member's own agent loop's channel; to make the member take it now, the swarm posts it and then interrupts the turn, so the loop's recovery finds the operator's redirect already queued and never waits. A pause is a boundary callback on the turn seam that waits while the member is paused; while held, a member's time limit stops and the wait is waiting time. Stopping a member is the seam's `end(origin="operator")`, and stopping the swarm is `stop("operator")`. The swarm records each message as drained by the member's loop or not, and which members an operator's stop ended. inspect_ai names the tool repairs of an interrupted conversation and finalises its cancelled tool events, so an interrupted member continues on every provider and its log shows what was cancelled.

## Why

An operator watching a multi-agent run needs to steer one member, pause to look, and stop one member that has gone the wrong way or is burning budget on a dead end, without ending the sample. The other surfaces do not reach a member chosen by name:

- **ACP** (an editor or the Inspect TUI attached to the sample) sends messages and interrupts, but binds whichever member opens its agent channel first, by chance, and no other ([swarm-communication.md The binder and ACP](swarm-communication.md#the-binder-and-acp)). It has no pause or stop.
- **The sample-level `inspect ctl` verbs** cancel the whole sample, cancel one tool call, pause every sample's model calls, and read events and messages, but know nothing of members.
- **A controller** starts members, ends them with `end()` and chooses the answer, but it is the eval author's code, not the operator's.

The pieces already existed: the turn seam holds a member between turns and ends one on request ([swarm-turn-seam.md](swarm-turn-seam.md)), and the agent channel carries operator messages and interrupts. This design puts them behind one operator surface, scriptable by agents that watch runs, with no client to attach.

## At a glance

The commands and what each does to a member are [Operators](../docs/operators.qmd)'s. Underneath, each action maps onto the swarm as follows:

| Action | A member (`--agent`) | The swarm (`--group`) |
|---|---|---|
| `message` | an operator `UserMessage` posted to the member's own loop; with `--interrupt`, then `interrupt(Cancel(reason="user_cancel"))` on that loop ([Messages](#messages)) | none (no broadcast) |
| `pause` / `resume` | the member's own flag, held by a turn-seam callback with origin `operator` ([Pause](#pause)) | a latch over the swarm's members, members started while it is set included |
| `stop` | the seam's `end(origin="operator")` ([Stop](#stop)) | the swarm's `stop("operator")` |

[Supported members](#supported-members) gives each member shape's actions.

## The inspect_ai registry and routes

`operator_group(name, group)` is a context manager that adds a group to the active sample's `ActiveSample.operator_groups` for its block and removes it on exit; outside a sample it does nothing. It raises `ValueError` when the sample already has a group of that name, or an agent of one of the group's names in another group. A group implements `OperatorGroup` (its `agents` mapping, `info()`, `pause()`, `resume()`, `stop()`), each agent `OperatorAgent` (`info()`, `message(text, interrupt=...)`, `pause()`, `resume()`, `stop()`), every mutation with `dry_run`. Each returns an `OperatorOutcome`: `changed`, a one-line `detail`, and `refused` when the action cannot apply. `info()` returns an `OperatorAgentInfo` (name, state, status, activity, paused, and `actions`, each action mapped to `None` when it would be accepted now or the reason it would not) or an `OperatorGroupInfo` (name, state, a `stop` category once stopping, paused, its agents). inspect_ai knows nothing of swarms: a group is any set of named agents some code in the sample can act on, and the swarm is its only registrant.

The control server calls a registrant's methods synchronously from its handlers. They run on the eval's loop, so an action is atomic with respect to the agents it acts on, but in the server's task and context, not the sample's, so a registrant that needs its context enters it itself. Methods must not await or do work proportional to a conversation's size, and outcomes and infos carry no agent-written text: names, lifecycle words, statuses and fixed sentences only.

`GET /evals/{eval_id}/sample/agents` lists the groups (`epoch` defaults to 1, as for other reads). `POST /evals/{eval_id}/sample/agent/{action}` takes a required `epoch` and exactly one of `agent` and `group`; `message` takes only `agent`, `interrupt` only with `message`, and its text as a JSON body, `{"text": "..."}`, not empty, since it is free and possibly multi-line where every other parameter is a scalar. An unknown sample, agent or group is a 404 that names the targets there are; a refused action is a 409 with the reason; otherwise the result has `changed`, `dry_run`, `target` and `detail`. A repeat that changes nothing is `changed: false`, never an error. The CLI sends every `agent` mutation once and never retries it: a repeated `message` would post a second message and make a second interrupt, and a repeated group action could reach a later swarm that registered the same group name in the same sample. A request whose response is lost is reported as an unknown outcome (`kind: "unknown_outcome"` under `--json`) that points at `list` rather than sending again. Handler 404 and 409 bodies are shown as written, so an unknown agent or group is not reported as a missing sample; an older server's stock 404 is reported as an inspect without the `sample agent` endpoints. The agent or group is an option, not a positional, because `EPOCH` is an optional positional. [control-channel.md](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/design/ctl/control-channel.md#other-directives) and the [control channel docs](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/docs/control-channel.qmd) own the rest of the surface.

### Interrupted conversations

Two inspect_ai rules make an interrupt safe on every provider and visible in the log; [Urgent messages and steering](swarm-communication.md#urgent-messages-and-steering) relies on them too.

- **Repairs are named.** `_repair()` answers each unanswered call of the last assistant message with a `ChatMessageTool` whose `function` is the call's name, so the repaired conversation converts on Bedrock, which refuses a tool result without one, and gives Google a matching function-response name. ACP's interrupts get the same repairs.
- **Tool events cancelled by an enclosing scope are finalised.** When an enclosing scope (an agent-channel interrupt, a sample limit) cancels a tool stage, the calls still pending get a `cancelled` error and a completion time, as generate finalises a cancelled `ModelEvent`. Events already finalised, by a completed call or by ACP before it interrupts, are left as they are.

## The swarm's group

`SwarmRun.run()` enters `operator_group()` before it claims the member names and the swarm's timeline, so a swarm refused for its group name claims nothing, and leaves it in `run()`'s `finally`, or at once if the setup before that `try` fails. It then saves its context (`contextvars.copy_context()`, after the bus and budget variables are set, as the members' context is) before any member starts; nothing awaits between the registration and that, so no action runs without it. The group, `SwarmOperator`, has one `MemberOperator` per roster member under the member's roster name, never a name the member chose for itself (`choose_name=True`), which is model output.

**Every action runs in the swarm's context.** Each `SwarmOperator` and `MemberOperator` method runs its body with `context.copy().run(...)`, so `stop()`'s grace, `end()`'s grace timer and everything else context-bound read the sample's limits, transcript and budget, as they do when a member or the controller calls them, rather than the control server's. `stop()` computes the effective grace before it records the reason, so an error there leaves the swarm as it was.

**Names.** The group is `swarm` for a swarm run directly in the sample, and `swarm:<member>` for a swarm run inside a member's work (read from `current_member` when the run starts), so a nested swarm's group is distinct from its outer swarm's and names the member that runs it. Member names do not clash, since they are unique in a sample across every swarm that runs in it (`claim_member_names()`). Two swarms running concurrently in one sample outside any member, or inside the same member, would share a group name; the registry's `ValueError` refuses the second when it starts, naming the group (decision: Ransom, 2026-11-02).

## The loop-bound hook

The gate calls `loop_bound(channel, passes_state)` synchronously when it binds a member's own loop (`turn_loop`), **after** its stop and end check and before its callbacks run. So a member whose swarm has begun to stop, or whose end was requested, is ended by the gate before the hook runs; the hook also returns at once if the swarm has a stop reason. Otherwise it subscribes the swarm's drain and turn-state observers on the loop ([Evidence](#evidence)), posts the messages kept for the member ([Messages](#messages)), and applies a pending pause ([Pause](#pause)), knowing whether the loop passes its state. `before_turn()` drains after the gate returns, so kept messages are drained at this first boundary, and a pause registered here holds the member at this same boundary.

## Messages

`MemberOperator.message(text, interrupt=...)` builds `ChatMessageUser(content=text, source="operator", metadata={"inspect_swarm": {"version": 1, "type": "operator", "id": "op-<n>"}})`, the id counted per swarm run, and then, by the member's state:

| Member | `interrupt=False` | `interrupt=True` |
|---|---|---|
| ended, bridged, pending, its own loop has returned, or its agent has ended and only its cleanup remains ([Cleaning up](#a-member)) | refused, with the reason | the same |
| ending: an end was requested (an operator's `stop`, a controller's `end()`), the swarm is stopping, or an error or a cancellation has begun to end the swarm's runtime (the stop guard, [Stop](#stop)) | refused: the gate ends the member at its next boundary before it drains a message | the same |
| running, its own loop not yet bound (setup before its first boundary, or an agent with no agent loop still running) | kept, posted by `loop_bound()`; a member that never binds a loop never receives it | the same: there is no turn to interrupt yet |
| running, its loop bound and not in a turn (`turn_active` false: between turns, or held at a boundary) | posted; the loop's next `before_turn()` returns it, after any hold | posted; nothing is interrupted, and the detail says the member takes it at its next turn, or when the hold ends |
| running, its loop in a turn (`turn_active` true), a pause pending or not | posted; it reaches the next turn, after the turn's tool calls and subagents finish | posted, then `interrupt(Cancel(reason="user_cancel"))`: the turn's model call, tool calls and subagents are cancelled, and `after_cancel()` returns the repairs and the message at once |

**Refusing a message to an ending member is best effort, as stops are** (decision: Ransom, 2026-11-09). The refusals cover the endings the swarm knows before the member's next boundary. A message accepted while a member ends some other way, such as its own expired time limit while a tool's cleanup still runs, is recorded `not_drained` and never delivered late.

**The own loop.** Messages are posted to the turn seam's `turn_loop`, the member's own top-level loop, through `channel._ref()`: the loop whose boundaries the seam holds, whose turn scope encloses its subagents' loops, and which no background task binds. The bus's `MemberContext.loop` is not used, since it may be a child loop.

**The row is read from the loop, not from the pause.** Which of the last two rows applies is decided by `turn_active` when the request arrives, never by the member's pause flag. A pause requested mid-turn takes effect at the next boundary, so until then `--interrupt` cancels the turn: `after_cancel()` returns the repairs and the message, react goes on to its next `before_turn()`, and the gate holds it there for the pending pause, whose callback the interrupt does not touch.

**Never an interrupt without a redirect.** The message is posted before the interrupt, in the same synchronous step, so the drain in `after_cancel()` always finds it and the loop never waits for an operator. If the turn ends on its own between the post and the cancellation's delivery, the scope's exit raises nothing and the message is drained at the next `before_turn()`.

**Drained, not delivered.** The swarm's record ends where the operator layer's control does: the message was accepted, and the member's loop took it off its channel at a given boundary, or never did because the member ended first. What happens after the drain belongs to the loop and the seam. React appends what the drain returned, and the append can be refused: a member's conversation is Inspect's limited list, which checks the message limit before it grows, so a conversation at its limit, or an interrupt's repairs and redirect exceeding the room left, ends the member with none of them appended. `after_cancel()` drains an interrupt's redirect and react appends it before the next `before_turn()`, so a seam callback at that boundary that restores an earlier snapshot, or any rewrite that leaves the redirect out, removes it, and nothing drains it again. The seam keeps that authority: the operator neither re-adds a message nor refuses a rewrite, and the seam's `changed` event records the removal with the callback's origin. Whether a drained message entered the conversation and reached a model is in the member's messages and the transcript's `ModelEvent` inputs.

**What an interrupt loses** is what any interrupt loses: the cancelled tool calls' results (a sandbox command may keep running), a cancelled synchronous subagent's result, and the usage of a cancelled model call, which the ledger reports as unknown. A member whose interrupted turn was running a nested swarm (a tool that calls `run(swarm(...))`) cancels that swarm: its members are cancelled, its ledger is written `interrupted`, and its group is removed; its member names stay taken in the sample, so a retry of the same tool with the same roster is refused by the member-name guard. A member's background work is not in its turn, so an interrupt does not cancel it.

**The member is not told by whom.** The message is a user-role operator turn like any other. Operator messages queued together, from `inspect ctl` and from ACP, are coalesced by `before_turn()`; the drain observer sees their original ids before the merge. If ACP drives the member, a `message` releases an ACP operator's pending interrupt as that operator's own redirect would; the swarm never calls ACP.

**A member in `swarm_wait`** is in a turn: a plain message waits until the wait returns (at most its `max_wait`), and `--interrupt` cancels the wait, which loses nothing. The detail line says which the member is doing.

## Pause

A pause is a hold at a turn boundary, never sooner. A member is paused while its own operator flag or its swarm's latch is set, and a pause reaches only the swarm it is addressed to ([Nested swarms](#nested-swarms)). While a member is paused, pausable and its own loop has bound, the swarm keeps one boundary callback registered on it with origin `operator`. At a boundary the callback waits, inside `suspend_working_limit()`, while the member is paused and pausable, and returns `None` when that changes; a resume, a new pause, a withdrawal or an unpausable mark wakes it to look again. When the member is no longer paused the callback is unregistered, so a member that is not paused has no operator callback and the seam's rules for members with callbacks do not apply to it. Until the loop binds (a pending member, or one in setup) the pause is recorded and registered from `loop_bound()`, before that boundary's callbacks run, so the member is held at boundary 0 with no model call. Registering only once the loop has reached the gate means a pause never makes a member `errored` under the seam's rule for members whose callbacks never ran. A member in a turn when it is paused goes on with that turn, and can finish there (a final submit or reply) without ever reaching the hold.

**The operator's callback never makes a member error** (decision: Ransom, 2026-11-02). The seam ends `errored` a member with callbacks whose loop passes no state, whose background work runs at a boundary, or that opens a second top-level loop after its first has closed ([Supported members](swarm-turn-seam.md#supported-members)). The operator's own registration never triggers these: every place the operator would hold a member goes through one guard, and wherever a member turns out not to be pausable the operator's callback is skipped or withdrawn, the member keeps running, and `list` shows why. Other callers' callbacks keep the seam's checks in force, including against background work admitted while the operator held the member ([The next holder's check](#pause), below).

- **The guard.** Before registering, for a direct pause, the latch and a pending pause at `loop_bound()` alike, the operator checks that the member has not ended and is not ending, and then that it is pausable: its agent has not ended (a member in its cleanup phase, [Cleaning up](#a-member), takes no more turns, and the seam refuses to register a callback on it); not bridged; not a `deepagent()` with background dispatch, read from its registry name and arguments (`seam_refusal()`); no background work started (`MemberContext.background`); and, once its loop has bound, a loop that passes its state and has not closed. The checks are synchronous and raise nothing, and a registration that raises all the same is caught and turned into an unpausable mark, so neither a pause nor a latch stops partway. A direct pause of an unpausable member is refused with the reason.
- **Deferred pauses.** A member whose loop has not bound yet (pending, or in setup such as react's MCP servers opening before its channel exists) passes the guard on what it can see, and its pause is accepted with a detail saying it takes effect at the first boundary. When the loop binds, `loop_bound()` runs the guard again with the loop's state known: the member is held at boundary 0, or, if the loop passes no state, left running and listed unpausable. Until then the member stays pausable, resumable and listed as `paused`.
- **Withdrawal.** What the guard cannot see in advance is caught where it happens. The operator's callback is registered through a withdrawable registration only the runtime uses. Wherever the gate would raise into the member because callbacks are registered (a boundary where the loop passes no state or where background work runs, a second top-level loop, and the first loop's close itself), it first withdraws the withdrawable callbacks: it unregisters them, wakes any that is waiting, and tells the operator the reason, which marks the member unpausable. If no other caller's callback remains, the member goes on as one with no callbacks; if one does, the seam's rule applies to it unchanged.
- **Background work while held.** The background owner tells the gate whenever a member starts background work, and the gate withdraws the operator's callback then, not at the next boundary. A custom native member whose wrapper owns a task group around its loop can pass it to a tool whose helper calls `background()` after the next boundary's hold has begun. The owner refuses new work while a member is held, which would end it `errored`; so if the callback **currently holding** the member is the operator's, the owner admits the work: the gate withdraws the operator's callbacks and marks the member unpausable ("starts background work"), the waiting callback wakes and returns `None`, the chain goes on, and the gate releases the member as after any hold. Callbacks that have already returned at this boundary do not count. If the holder is another caller's, the owner's refusal applies unchanged, and the operator's callback is withdrawn all the same.
- **The next holder's check.** Work admitted while the operator held the member may still run when the chain advances to a later caller's callback. So before each callback in the chain the gate checks running background work, as it does before a chain begins: a withdrawable callback is withdrawn, and another caller's meets the seam's background rule (the member ends `errored`), so no caller holds a member alongside running background work.
- **Unpausable is final for the run.** A member marked unpausable is never held by the operator again in that run: a later direct pause is refused with the recorded reason, and the latch skips it and names it in its detail. After a native withdrawal (background work, a loop that passes no state, a closed loop) the member's own flag stays as the operator set it, and `resume` still clears it.

So members with background work are never paused (decision: Ransom, 2026-10-30), matching the seam, which refuses to hold them because their background work would go on generating. Some are refused up front; one the guard cannot see, such as a `deepagent(background=True)` built by an `@agent` function of its own, is paused until it first dispatches background work, when its pause is withdrawn. Messages, `--interrupt` and `stop` still reach them; an operator who must freeze one uses `inspect ctl task pause --now`, which holds every sample in the task at its next model call.

**The whole swarm.** `SwarmOperator.pause()` sets the latch, which registers a hold at the next boundary of every pausable member, and at the first boundary of members the controller starts while it is set. Its detail names the members that cannot be paused, with their reasons. The latch is not a fan-out of member pauses, so resuming it clears only the latch: members' own flags stay, and the detail names the members whose own pause can still hold them (running, not ending, within their time limit, pausable). Conversely `resume --agent` while the latch is set clears only the member's own flag; `changed` reports that flag, not whether the member is released, and the detail names the latch when it can still hold the member. `list` reports `paused` true only while a pause is set and can still hold the member. A pause of the swarm, or of a member, is refused once the swarm is stopping.

**What a pause does not stop.** The controller keeps running and consuming events during a pause of the swarm. Members that finish before reaching their hold, and members that cannot be paused, go on producing events; a member actually held by the operator remains running. Inspect's own `pause --now` parks model calls independently of the seam.

**Composition.** An operator pause is one more boundary callback, so when it runs relative to other callers' callbacks, including callbacks registered, resumed or renewed while a scheduler's callback is already holding the member, follows the turn seam's [callback contract](swarm-turn-seam.md#the-callback-contract). Messages posted to a paused member are drained when the hold ends.

**Time.** A hold is a seam hold ([Time](swarm-turn-seam.md#time)): the member's time limit does not run while it is held, and the operator's wait is waiting time. [Operators, Time while paused](../docs/operators.qmd#time-while-paused) gives the table. The swarm's time cap and the sample's time limit are deadlines for the whole run, so they keep counting, as inspect's own hard pause keeps a sample's time limit running: wall clock is the operator's risk (decision: Ransom, 2026-10-30). A long pause can therefore use up the cap and start the swarm's stop while members are held. The operator can retune the sample's time limit with `inspect ctl config`; the swarm's cap is not retunable.

**`swarm_wait`.** The seam counts a held member as not active, so that members waiting on a scheduler's or a persistent member's hold are released. An operator's pause is different: the operator means to resume the member, so its siblings keep waiting for it rather than conclude that everyone is done (decision: Ransom, 2026-11-02). The gate records which callback it is awaiting, and the all-waiting check counts a member as active while that callback is the operator's pause, told apart by its withdrawable registration, not by its origin, which any caller may also use (`MemberContext.operator_hold`). Callbacks that have returned or not yet run do not count. The gate rechecks the waits whenever the holder changes between the operator's pause and another callback, as well as at hold and release. So while an operator callback actually holds a member, that member prevents an `all_waiting` release. The latch alone does not: until members reach their holds, the ordinary all-waiting rules apply.

## Nested swarms

A swarm run inside a member's work (a tool that calls `run(swarm(...))`, or `member(swarm(...))`) registers its own group, `swarm:<member>`, and its members are paused, resumed and stopped through that group or by name, like any swarm's. Pausing the outer member, or the outer swarm, holds only the outer member's own loop at its next boundary (a `member(swarm(...))` member has none, so nothing is held); the nested swarm's members keep running until paused through their own group (decision: Ransom, 2026-11-02). The outer member counts as held only once its own loop reaches a boundary; until then its turn runs the inner swarm, and its time limit runs.

## Stop

### A member

`MemberOperator.stop()` calls `end(origin="operator")` on the member, in the swarm's context. A held member ends at once; a member in a turn or in setup, a pause pending or not, ends `stopped` at its next boundary or on a normal return, its next model call refused, or `cancelled` when its turn, setup or cleanup outlasts the effective grace ([Ending a member from outside the chain](swarm-turn-seam.md#the-callback-contract)). The rest of the swarm goes on, and the controller sees its `MemberEnded` as for any member. It works for every member shape, bridged ones included.

**Every phase of a member's run has a path to its end**, for any end request whatever its origin:

- **Pending.** An end requested before the member starts is consumed when the controller starts it, before its sandboxes, background owner, agent build or agent call: the member ends `stopped` with no setup and no model call. A setup-blocked `react()` (an MCP server that never answers), a channel-less agent and a bridged CLI all end at once.
- **Running, before its first boundary** (agent build, MCP setup, a channel-less or bridged agent with no boundary at all). The member counts as mid-turn: the request closes its lever and arms the same grace timer as for a turn, so a member that never reaches a boundary is cancelled when the effective grace runs out, without relying on the swarm's or the sample's deadline.
- **Draining.** A member whose agent has returned stays running while its background work drains, under the drain's own grace, so the request arms no timer. The member wrapper checks for an end request once more after the drain, before the cleanup below: a return without a submission (`unsubmitted`) becomes `stopped`; a status the return already decided otherwise (`submitted`, a member limit, `stopped`, `swarm_cap`) is kept.
- **Cleaning up.** Once the agent and its background work have ended and its status is decided (whether an end request decided it included), the wrapper marks the member's gate finished, synchronously, and only then awaits its cleanup: under users isolation, stopping the processes the member left running, which never raises and is shielded from cancellation. Until that ends the member is still running, with its own loop closed or never bound, but it takes no more turns: a message and a pause are refused ("its agent has ended"), the seam refuses to register any caller's callback, and an operator's stop changes nothing (`changed: false`), so it neither changes the member's status nor makes `operator` its `end_origin`, which were decided before the mark. The end-request grace timer and the swarm's hard stop skip such a member, so its cleanup is not recorded as cancelled work. Without users isolation there is nothing to await, and the member ends as soon as it is marked.

**A stop ends work only; it never withdraws an answer** (decision: Ransom, 2026-11-04). Answers the member gave before the stop stay eligible, under `first`, `last`, a controller's earlier pick and a later `choose_answer()`, exactly as after a controller's `end()`: a persistent member's earlier answers, whatever its status; an idle persistent member, which ends `submitted` with its last answer as its output; and the submission of a member whose agent returned before the stop and whose background work is draining. A queued `MemberIdle` is an ordinary submission notice. A member whose agent returns after the request ends `stopped`, whatever its output.

**Repeats.** A second stop, a stop of an ended member or of one cleaning up, a stop of a pending member once the swarm is stopping (no member starts then), and a stop once an error or a cancellation has begun to end the swarm's runtime change nothing (`changed: false`).

### The stop guard

The runtime takes no new stop while it unwinds after an error or a cancellation, since a stop would start a grace timer in a task group that is closing. `_active()` is false before the runtime starts, once its supervisor task has ended, once an error from a member or the controller is known, and once a cancellation has reached the runtime. The error is latched where it is first known: in the member wrapper before it leaves the background owner (whose teardown can wait on shielded cleanup), in the owner as a background task's error escapes it, before a member's `errored` result is published, and as an error leaves the controller's task, before the task group reacts. An operator's action runs in another task, so the guard asks the swarm's task, saved by `run()` as an anyio `TaskInfo`, through `has_pending_cancellation()`, and reads the runtime scope's `cancel_called` for the time after that task has taken the cancellation.

**The guard is best effort; the record is not** (decision: Ransom, 2026-11-05). A stop that reaches the run during its teardown before the guard knows, by a path it does not see (a member's error raised in a group with a cancellation is one), is accepted and may answer `changed: true` for a change that never shows in the record. What holds is the record: `_account()` writes the ledger's `stop_reason` as `null` instead of `operator` whenever the run is known to fail or be cancelled when the ledger is written, whichever path led there, an operator's stop made before the failure included. That covers a run that did not complete its final step, or whose result record or metrics could not be written, which is why `_account()` writes the metrics before the ledger. One failure comes after it: `_account()` fills the swarm's timeline once the ledger is written, so that the timeline holds the ledger and the metrics, and `run()` raises an error from that fill without revising the ledger, so a run that fails only there keeps `stop_reason` `operator`. The rule covers the run's own ending only (`stop_reason`, `interrupted`, `ended_by`, the swarm's error): each member keeps the ending it actually had, so a held member a late stop ends records `stopped` with `end_origin` `operator` (decision: Ransom, 2026-11-05).

### The swarm

`SwarmOperator.stop()` calls `stop("operator")`, in the swarm's context, and `operator` is one of the closed set of stop reasons ([swarm-limits.md Stopping](swarm-limits.md#stopping)). It is the swarm's own orderly stop: the controller's run is cancelled, members' levers close, held members end at once, grace and the hard stop follow, and the final step chooses the answer. The swarm then returns, so the sample continues to its scorers, and the ledger's `stop_reason` is `operator` with `ended_by` unset. A stop of a swarm already stopping is `changed: false`. An operator who wants the sample itself ended uses `inspect ctl sample cancel`, recorded as `ended_by: operator`.

## The list

`MemberOperator.info()` gives the member's roster name, its state and status, whether it is `paused` ([Pause](#pause)), its activity, and `actions`. Activity is `not_started`, `held` while held, `in_turn` or `between_turns` from its own loop's `turn_active`, `unknown` for a running member whose loop has not bound or has closed (setup, a bridged member, an agent with no agent loop), and `ended`. `actions` maps each action to `None` when it would be accepted now or the reason it would be refused, from the same checks the action makes; `stop` is always available, and a message that would be kept until the loop binds counts as accepted. `SwarmOperator.info()` adds the swarm's state (`running` or `stopping`), whether the latch is set, and once stopping a `stop` category: the stop reason when it is one of the swarm's own (`operator`, `all_done`, `submitted`, `verified`, `quiescence`, `swarm_cap`, `swarm_time`), and `controller` for any `controller:<reason>`, so a controller's free text never reaches the list.

## Evidence

The swarm writes evidence from the member's side, never from the control server's handler. The fields are documented in [Analysis, Operator actions](../docs/analysis.qmd#operator-actions) and the event kinds in [swarm-event-types.md](swarm-event-types.md#swarmevent).

- **`operator_message`**, one `SwarmEvent` per message the swarm accepted, with `outcome` `drained` or `not_drained`. `loop_bound()` subscribes a drain observer and a turn-state observer on the member's own loop; both run synchronously in the loop's task, so in the member's span, and the drain observer is told of the drained items before `before_turn()` coalesces them, so it sees the swarm's own message ids. The turn-state observer notes when the turn of the gate's latest boundary starts. When the drain observer sees one of the swarm's messages it writes the event at once. If the latest boundary's turn has not started, `before_turn()` drained it at that boundary, after its callbacks: `boundary` is the gate's latest index (`Boundary.index`) and `recovery` false. Otherwise `after_cancel()` drained it after that turn was interrupted: `boundary` is the next index, the one the loop goes on to, and `recovery` true. The loop need not reach that boundary: react's append can be refused, or the member can end first. A message still kept or queued when the member ends is written by the runtime's `_end()`, before the `member_result`, as `not_drained` with `boundary` and `recovery` `null`. A drained message is never written again. Neither outcome says a model saw the message ([Messages](#messages)), and the text is not in the event.
- **Pauses** need no kind of their own: every boundary at which the operator's callback ran is the seam's `boundary` event, with `operator` in its `origins` and the time held in `held_for`, and the seam's `holds` and `held_time` metrics include it.
- **`end_origin`.** A member's status says how it ended but not who asked: `stopped` is also the swarm's soft stop, `cancelled` also the hard stop, and the seam's `boundary` event is written only where callbacks ran. So every member ending records `end_origin`, the origin of the end request that decided the member's status (`operator`, or another caller's origin given to `end()`), or `null` when none did (a submission it kept, a member limit, the swarm's stop). The member wrapper sets it wherever it honours an end request: consumed before setup, at a boundary, on a normal return, by the grace timer's cancellation, after the drain of a return with no submission, and for an idle persistent member it ends `submitted`, including when another stop closed the member's lever first. It is in the `member_result` event, `MemberResult.end_origin` in the result record and `MemberLedger.end_origin`. The swarm's own stop stays in `stop_reason`.

A message's interrupt is also visible in the conversation (the named repair `Tool call cancelled by user.`) and as the finalised cancelled `ToolEvent`.

## Supported members

Operator actions serve the member shapes in the examples, the docs and the tests: `react()` and `deepagent()` members, with `swarm_tools()` or not; `deepagent(background=...)` members and custom agents that call `background()`; inspect_swe's bridged agents; nested swarms run by a member; and test-only custom agents that generate without an agent channel or only sleep. ACP agents are refused as members ([Restrictions](../docs/restrictions.qmd)).

| Member | `message` | `--interrupt` | `pause` | `stop` |
|---|---|---|---|---|
| `react()`, `react(submit=False)`, `deepagent()` | yes | yes | its loop at its next boundary | yes |
| `deepagent(background=...)`, custom agents that have started `background()` work | yes, to the own loop | yes; background work goes on | refused up front when the guard sees it, otherwise withdrawn when background work starts | yes |
| custom agent whose loop passes its state | yes | yes | its loop at its next boundary | yes |
| custom agent whose loop passes no state, or that runs a second loop after the first | yes, to its bound loop while open | the same | withdrawn at its first such boundary, or when its first loop closes; it keeps running | yes |
| a member running a nested swarm (`member(swarm(...))`, or a tool that runs one) | to its own loop, if it has one | the same | its own loop, if any; the nested swarm's members only through their group | yes |
| custom agent with no agent channel (test-only `generator()`, `sleeper()`) | kept, recorded `not_drained` | the same | accepted, never held | yes |
| bridged: declared, or an inspect_swe agent (Claude Code, Codex, Gemini CLI, OpenCode, Kimi Code, mini-SWE-agent, Antigravity) | refused | refused | refused | yes |
| nested loops (subagents) | not addressable: their member's own loop is | | | |

Bridged members are stop-only (decision: Ransom, 2026-10-30): their CLI runs its own turns through `sandbox_agent_bridge` and opens no agent channel, so nothing the swarm posts reaches it and the seam cannot hold it. A member is bridged when it is declared, `member(..., bridged=True)`, or is an inspect_swe agent; the runtime does not detect a bridge as the member runs (decision: Ransom, 2026-11-02). An undeclared custom or wrapped bridged agent is offered `pause` and `message`, and neither takes effect: it binds no turn loop, so a pause never holds it and a message is recorded `not_drained`; `bridged=True` is the remedy. A native member that runs a bridged subagent in a tool call is native, and a pause holds it at its next boundary.

## Decisions

- 2026-10-30: operator controls are not available on trio, where inspect_ai's control server does not start (decision: Ransom, 2026-10-30).
- 2026-10-30: members with background work are never paused, as the seam never holds them; `inspect ctl task pause --now` is the fallback (decision: Ransom, 2026-10-30).
- 2026-10-30: bridged members are stop-only (decision: Ransom, 2026-10-30).
- 2026-10-30: `inspect ctl` is the first operator surface; ACP sessions per member can be built later on the same registry (decision: Ransom, 2026-10-30).
- 2026-10-30: the swarm's time cap and the sample's time limit keep counting while paused; wall clock is the operator's risk (decision: Ransom, 2026-10-30).
- 2026-11-02: the operator's pause never makes a member error; its callback is skipped or withdrawn where the seam would raise, and other callers' checks stay in force (decision: Ransom, 2026-11-02).
- 2026-11-02: a member held by the operator's pause counts as active for `swarm_wait` (decision: Ransom, 2026-11-02).
- 2026-11-02: a nested swarm is paused through its own group, not with its outer member (decision: Ransom, 2026-11-02).
- 2026-11-02: two concurrent swarms with the same group name in one sample are refused at the second's start (decision: Ransom, 2026-11-02).
- 2026-11-04: a stop ends work only and never withdraws an answer (decision: Ransom, 2026-11-04).
- 2026-11-05: the stop guard is best effort; a run that fails or is cancelled records that ending, and members keep their own (decision: Ransom, 2026-11-05).
- 2026-11-09: refusing a message to an ending member is best effort, and an accepted message is never delivered late (decision: Ransom, 2026-11-09).

## Alternatives considered

- **ACP sessions per member as the first surface.** An editor or the Inspect TUI would attach to `worker-2` as to a single-agent sample. It reworks ACP's per-sample transport into per-agent sessions, needs `--acp-server` and an attached client, and has no pause or stop.
- **`Steer` items for operator messages.** `Steer` is for producer-composed content that must not count as the operator's redirect. An operator's message is the redirect, and `UserMessage` satisfies `after_cancel()`'s wait, which is what makes an interrupt safe.
- **Confirming that a model received the message**, by matching its id in the member's `ModelEvent` inputs. Input preparation merges consecutive user messages under a new id, and a seam callback may make model calls at a boundary with a conversation it then rewrites, so a correct matcher would have to follow the provider's normalisation. The swarm records the drain, which it controls; the `ModelEvent` inputs show what each call received.
- **Re-adding a redirect a rewrite removed**, or refusing such a rewrite. It overrides the seam's rewrite authority, which a snapshot restore or a defence uses deliberately.
- **Pausing members with background work** by holding the own loop and parking background tasks at their next model call through a new hold in inspect's generate gate. It needed that hold, its composition across nested swarms, an exception to the seam's background rules, a rule for background work that starts more, and `swarm_wait` changes for parked work.
- **Pausing a nested swarm with its outer member**, through a parent chain from each nested group to the outer member. It needed propagation, its interaction with withdrawals, and a third pause source in every guard; the nested group is already addressable by name.
- **A preemptive pause** (interrupt, then hold). The interrupt's recovery waits in `after_cancel()`, which is not a boundary; releasing it would put text the operator did not write in the conversation. An operator who needs the member stopped now sends `message --interrupt` or cancels the tool call, then pauses.
- **Registering the operator callback on every member at its start**, idle until a pause. The seam would then end `errored` any custom member with no agent loop.
- **Group actions as fan-out over members.** A loop misses members the controller starts later, and stopping every member is not the swarm's stop: it skips the controller's cancellation and stop reason, and the controller would see every member end and return `all_done`.
- **Reserving `swarm` as a member name** for one namespace of agents and groups. `member(swarm(...))` defaults its name to `swarm`, so reserving it would refuse an existing shape; `--agent` and `--group` are separate options instead.

## Compatibility

- **Records.** `operator` is a ledger `stop_reason`; analysis code that matches stop reasons exhaustively must include it ([Analysis, The ledger](../docs/analysis.qmd#the-ledger)). `end_origin` on `MemberResult` and `MemberLedger` defaults to `None`, so records and ledgers written before it load. `operator_message` is a `SwarmEvent` kind ([swarm-event-types.md](swarm-event-types.md)).
- **End requests.** The pending, before-first-boundary and draining paths ([Stop](#stop)) apply to every end request, a controller's `end()` included: a pending member it ends skips setup when started, a member still in setup gets the grace, and a draining member with no submission ends `stopped` instead of `unsubmitted`.
- **Group names.** Every swarm run in a sample registers a group, even when no operator acts, so two swarms running concurrently in one sample outside any member, or inside the same member, are refused ([The swarm's group](#the-swarms-group)). No use of that shape exists in this repo or its docs.
- **Without an operator** no callback is registered, no message is posted and no interrupt is made.

## Security

- **Who can act.** The control channel binds an AF_UNIX socket with a peer-UID check, so only the eval's own user can act, as for `sample cancel` and `cancel-tool-call`. The operator, human or agent, is trusted: their text goes into a member's conversation in the user role, which is what an operator message is.
- **No member reaches the registry.** No tool exposes it. A member that can reach the host's socket from its sandbox is outside this design and could already cancel the sample.
- **No agent text leaves through it.** Lists and outcomes carry roster names chosen by the eval author, lifecycle words, statuses, stop categories from a closed set and fixed sentences; never a name a member chose, a controller's free-text stop reason, a message, a tool result or an agent-written error. The evidence holds ids, flags and indices, not text.
- **Untrusted input.** The message text comes from the operator, not from a model, and is passed through unchanged, never parsed. Agent and group names in requests are only looked up in dicts; unknown ones are answered with the registered names.

## Not this design

- **ACP sessions per member**, built on this registry: one ACP target per registered agent, with its own binding and a transcript filtered to its span, so that an editor or the TUI can drive any member.
- **Messages, interrupts and pauses for bridged members**: each CLI's inspect_swe driver would read its agent channel at the CLI's safe points, relaunch the CLI on its own conversation with the operator's message, and be paused there or at its model requests.
- **Holding a member during an ACP operator's interrupt recovery.** An ACP interrupt without a redirect still leaves the ACP-bound member waiting in `after_cancel()`, outside the seam; operators through `inspect ctl` never leave a member there.
- **Pausing the swarm's controller** with the swarm, and operator controls for controllers' own model calls.
- **A "message every member" verb**, if shell loops over `message` turn out not to be enough.
- **Confirmed model-input delivery** of operator messages, through inspect's input normalisation and leaving out a seam callback's own model calls.
- **Operator targets for single-agent samples** (the sample's top-level `react()`), which ACP serves.
- **A retunable swarm time cap**, if operators' long pauses turn out to need one.
- **Operator controls on trio**, which would need inspect_ai's control server to run there.
- **Pausing members with background work**, which the seam's background rules would have to allow ([Alternatives considered](#alternatives-considered)).
- **A failed timeline fill after an operator's stop.** The ledger is written before the timeline is filled, so a run that fails only there keeps `stop_reason` `operator` ([The stop guard](#the-stop-guard)); [Operators, Stopping the swarm](../docs/operators.qmd#stopping-the-swarm) and [Analysis, The ledger](../docs/analysis.qmd#the-ledger) state the broader guarantee. Closing the gap, in the runtime or in those docs, is separate work.
