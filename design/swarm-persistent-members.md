# Inspect Swarm: persistent members

## Overview

A persistent member stays available after it answers. It is declared on its record, `member(worker, persistent=True)`, and runs inside one `react()` (or `deepagent()`) loop for its whole life. When it submits in a turn that calls no handoff, or a `react(submit=False)` member gives a tool-free reply, the swarm records that as one of its *answers* and holds the member *idle* at its next turn boundary instead of letting the loop return. The controller hears `MemberIdle` and hands the member its next piece of work with `SwarmControl.wake(member, input)`, which appends the input to the member's conversation, so each new *activation* keeps everything the member has seen and done. While a member is idle, a write that would end a whole-board `swarm_wait` of its own loop reaches the controller as `MemberNews`, and the controller decides whether to wake it. A swarm whose members are all pending, idle or ended, with no submission or answer still waiting for its verdict and no event waiting, is *quiescent*: the controller's `events()` iterator ends.

The mechanism is the turn seam ([swarm-turn-seam.md](swarm-turn-seam.md)) plus one private hook in inspect_ai: a react loop that has an answer and would return it first asks the swarm's turn gate, through `after_answer()`, and for a persistent member the gate records the answer and says "continue", so the loop goes on to its next turn boundary, where the gate holds the member idle. Anything else that ends the loop (a refusal, an overflow, an `on_continue` that stops it, a submitting turn that also called a handoff) is not an answer and ends the member `unsubmitted`, with its earlier answers still candidates. Every answer is a candidate for the swarm's answer: `first` and `last` choose across all answers, `choose_answer()` takes the member's latest, and the result record keeps the time of each answer and which one was chosen. An idle member that a stop or `end()` reaches ends `submitted`, its last answer its output. With a result contract that keys or verifies, each answer is a submission for the contract: it is keyed when it is given and verified while the swarm runs, and the member goes idle, with `MemberIdle` carrying the verdict, only once that verdict is taken. The chain's `verify` then ranks each answer by its own verdict, `vote` counts the member once by its latest answer, `leaderless()` under a chain led by `verify` stops on a passing `MemberIdle`, and `baseline()` refuses a persistent member. Only a member whose agent is itself a `react()`, `react(submit=False)` or `deepagent()` loop without background dispatch can persist, given directly or returned by a builder; every other agent is refused before it runs.

The code is `MemberGate.after_answer()` and the idle hold in [`_seam.py`](../src/inspect_swarm/_seam.py); `wake()`, the states, `MemberIdle`, `MemberNews`, the answers and each answer's key and verdict in [`_control.py`](../src/inspect_swarm/_controller/_control.py); `AnswerResult` and its writing in [`_record.py`](../src/inspect_swarm/_record.py); `persistent_refusal()`, `output_status()` and the endings in [`_member.py`](../src/inspect_swarm/_member.py); `_check_persistent()` in [`_swarm.py`](../src/inspect_swarm/_swarm.py); the candidates in [`_final.py`](../src/inspect_swarm/_final.py); the news check in [`_bus.py`](../src/inspect_swarm/_bus/_bus.py); and in inspect_ai, the private `after_answer()`, `TurnLoop` and `turn_loop()` in `inspect_ai.agent._channel.gate`, the calls to it in `react()`, and `watch_handoffs()` in `inspect_ai.model._call_tools`. The user docs are [Members, Persistent members](../docs/members.qmd#persistent-members) and the statuses in [How a member ends](../docs/members.qmd#how-a-member-ends), [Controllers, Persistent members](../docs/controllers.qmd#persistent-members) and [News for idle members](../docs/controllers.qmd#news-for-idle-members), the answer rules in [Scoring](../docs/scoring.qmd#the-answer), and the record, metrics and evidence in [Analysis, Persistent members](../docs/analysis.qmd#persistent-members). [`examples/lead_and_workers.py`](../examples/lead_and_workers.py) is a lead that hands out work to persistent workers on the shared memory.

## Which agents can persist

A persistent member's agent must itself be a `react()`, `react(submit=False)` or `deepagent()` loop, given directly or returned as it is by a builder. The loop the seam binds is then the member's whole agent, so when that loop answers the member has answered, and no code of the member's own waits after the loop to check or change the result. A builder that returns the loop runs before the loop and not after it, so it is not such code; a wrapper that awaits the loop is. The gate cannot see code that waits after an inner loop, so the loop is recognized by its provenance before it runs.

**The loop's mark.** A loop's registry name says nothing about what a member runs: `@agent` retags the object a builder returns with the builder's own name, and a `functools.wraps` copy carries the inner loop's name and parameters. So inspect_ai's private gate module has a mark, `TurnLoop(loop, background)`, which `react()`, `react(submit=False)` and `deepagent()` set on their inner function before `@agent` wraps it (`deepagent()` with its `background` setting). `turn_loop(agent)` returns the mark only when the agent's running marker points at the agent itself and its `__wrapped__` is the marked function. The mark therefore survives what keeps the object (a builder's retagging, `agent_with()`, `react(name=...)`) and fails for a `functools.wraps` copy, whose marker points elsewhere, and for an `@agent` builder whose own function wraps the loop, whose `__wrapped__` is that function.

**When it is checked.** On the object the member will run, with nothing built early:

- A built agent (`record.agent`) at `swarm()`, in `_check_persistent()` among the roster checks, whatever the channels, so the task fails before any model call.
- A factory member's agent in its own run, on the agent `build_member()` returns, before it is called. A member rebuilt from a log is checked the same way. The refusal fails the swarm as any error foreign to the swarm does, before that member's first generation.

The refusals, each a `ValueError` naming the member:

- An agent with no valid mark: inspect_swe's bridged CLIs, whose own turns the seam cannot hold; custom loops, which cannot ask the private hook at their answers; wrappers with completion logic after their inner loop, such as `checked_solver()` in `examples/stop_on_proof.py` and `prover()` in `examples/proof_swarm.py`, whose inner answer would be recorded before the wrapper's check ran; and `functools.wraps` copies of the loops.
- A mark with `background` set: `deepagent(background=True)` or an integer `background`, directly or from a builder. The seam does not hold background work.
- A member declared `bridged=True`, whatever its agent, at `swarm()`.

A result contract does not limit which members can persist; with an `answer_key` or a `verifier`, each answer is keyed and verified ([Keys and verdicts](#keys-and-verdicts)).

**The board's reader must be the turn loop.** A persistent member's idle news is computed for the loop the wake continues, so the loop that reads the board for the member (the bus's binding, `MemberContext.loop`) must be the loop the seam holds (`MemberContext.turn_loop`). When `swarm_tools()` is given only to a subagent (`research(extra_tools=[swarm_tools()])` under a `deepagent()` whose own tools omit them), the bus binds a child loop that closes when the child returns, and later children read under spans of their own, so no loop that survives the answer could clear the news and a controller waking on news would wake the member again and again. The gate refuses that member, but only in a swarm with a waiting channel (one that sets `max_wait`: `shared_memory()` and `messages()`). With `channels=[]` or only `filesystem()` there is no news, so the binding does not matter and the member persists. At every boundary of a persistent member's turn loop, and in every `after_answer()` from it, the gate raises `RuntimeError` if the swarm has a waiting channel and the bus is bound to another loop. Both checks run in the member's top-level loop, and the child that bound the bus runs inside one of its turns, so the error comes before any answer from that turn is recorded or any news is asked. A member whose top-level loop has `swarm_tools()` and passes them to subagents too is unaffected: the top-level loop resolves its tools first and binds.

A persistent member also counts for the seam's never-reached rule ([swarm-turn-seam.md Supported members](swarm-turn-seam.md#supported-members)): a member whose own loop never reached the gate fails with a `RuntimeError` saying it could not be held after an answer. A react or deepagent loop always reaches a boundary before its first generation, so the rule is a backstop.

## Continuing past an answer

### The inspect_ai hook

`inspect_ai.agent._channel.gate` has a function `after_answer(channel, state)` and a matching entry point on its private `TurnGate` protocol. A react loop that has an answer and would return it calls the function first, and continues to its next turn instead of returning when it returns `True`. Without a gate on the channel (a loop outside a swarm, or the inert channel) it returns `False` at once, so the loops behave as they do without the swarm. The hook is private, as `before_turn()`'s gate is: inspect_ai's public API has no `after_answer()`, and only its own loops can persist.

### What is an answer

An answer counts only when the loop gives it in its own answer form. The loops call `after_answer()` at these exits and nowhere else:

- **A submitting `react()`**: a submission with its attempts used up, and a submission whose check passed, each only when the turn called no handoff. When the gate says continue, the loop sets its attempt count back to 0, so each activation has its configured attempts, and goes to the top of the loop without calling `on_continue`, as a submission that ends the loop skips it. The submit tool's call and result stay in the conversation, so the model sees that it answered; `keep_in_messages=False` still removes them if the loop ever returns.
- **`react(submit=False)`**: a tool-free reply with no `on_continue`, and an `on_continue` that returns `False` after a tool-free reply. The loop reads whether the turn replied from the turn's own generated message, before any tool runs.

A turn's own submission and reply are the only answers because a handoff replaces the turn's output with its child's: a parent whose turn called a handoff whose child ended tool-free reaches `react(submit=False)`'s tool-free exit with the child's output, and a submitting `react()` finds a submission by the tool result's function name alone, so a handoff whose output filter keeps the child's tool messages can bring back a child's same-named result as the parent's submission. So a submitting `react()` asks only when the turn called no handoff. It learns that from the executor: it calls `execute_tools()` inside `watch_handoffs()`, and that `execute_tools()` call sets the watch's `called` flag when one of the message's tool calls resolves, as dispatch resolves it, to a handoff. The executor takes the watch and clears it for its own tool resolution and tool bodies, so an `execute_tools()` nested in one of the turn's tools (an `as_tool()` child's loop) cannot mark the parent's. The flag comes from the calls resolved, not from what the tools returned, since a failed handoff returns no output. Every other caller of `execute_tools()` sees no change.

The gate then decides whether the output is one the member wrapper would classify `submitted` if the loop returned it, with `output_status()`, the rule a non-persistent member's normal return uses (an empty output is `submitted`; otherwise `content_filter` and `model_length` are `unsubmitted`). A refusal that makes a valid submit call, or a `react(submit=False)` tool-free refusal, gets `False`: the loop returns from the exit it was at, with its attempts not reset, nothing recorded and no `MemberIdle`, and the member ends `unsubmitted`.

The other exits never ask, and end the loop as they would without the swarm: a third consecutive refusal, an unrecoverable overflow, and the *cut-offs*, where the loop stops outside the answer form (a submitting `react()`'s `on_continue` returning `False` after any turn; `react(submit=False)`'s returning `False` after a turn that made tool calls, or its tool-free exit after a handoff; a submitting `react()` at a submission exit in a turn that called a handoff; the same in a `deepagent()`, whose top-level loop is a `react()`). A cut-off is how a turn limiter such as inspect_evals' `TurnLimit` stops a loop, not an answer and not a fault: the member ends `unsubmitted`, its returned output never recorded, and the swarm goes on. The `on_continue` is the loop's own, so a turn limiter counts across the member's whole life.

### The gate's `after_answer()`

`MemberGate.after_answer()` does not await between the answer and the loop's next boundary:

1. If the call is not from the member's turn loop (the member's own task and the bound channel, not yet closed), or the member is not persistent, return `False`. A nested loop's answer, such as a subagent's, returns to its caller.
2. Apply the reader rule above.
3. If `end()` was requested for the member, return `False`: the loop returns, and the member ends `stopped`, that submission not an answer, as the seam rules for an end request that a final submission meets.
4. If `output_status(state.output)` is not `submitted`, return `False`.
5. Otherwise record the answer (a detached deep copy of the output, with the swarm time), write its `answer` evidence, settle the provisional answer, key it and put it on the verification queue when the result contract asks ([Keys and verdicts](#keys-and-verdicts)), set the member's *answered* mark, and return `True`. The member stays `running` until its hold is admitted and its answer's verdict is settled.

A swarm stop does not change step 5: an answer given while the swarm stops is recorded, and the boundary that follows ends the member at once with the answered mark set, so `submitted`.

## The idle hold

The loop goes from `after_answer()` to `before_turn()` with no generation or tool call between. At that boundary, because the answered mark is set, the gate takes the idle path rather than the seam's ordinary one:

1. **Admission.** In order: a stop or end request, a loop that passes no state, background work running, the reader rule, and the member's time limit already reached. Each refusal first sets the member `ending`, synchronously, then ends it: a stop or end through the member's lever, so `submitted` with the answered mark set; a missing state, background work or the reader rule with a `RuntimeError`; an overdue time limit through Inspect's limit path, `member_limit:time`. The hold is admitted even with no boundary callback registered.
2. **Idle.** Once the time limit is paused and the member marked held, the gate tells the runtime that the hold is admitted, with no `await` since the pause. Unless the member is *checking*, its latest answer still waiting for its verdict ([Keys and verdicts](#keys-and-verdicts)), the runtime sets the member `idle`, queues `MemberIdle(member, answer, news, verdict)` and notifies the controller's iterator in that one synchronous step; a checking member stays `running`, held, until its verdict is settled, and the runtime publishes it then. Either way the gate then waits for the wake inside the hold's cancel scope and inside `suspend_working_limit()`, so idle time is waiting time for the sample's working limit. A stop or `end()` sets the member `ending` and cancels the wait, and the hold's release ends the member `submitted`.
3. **Wake.** The wake's input is appended to the staged conversation as the runtime's change (a `changed` event with origin `swarm`), the boundary's `after` becomes `"wake"` and its `activation` the new activation's index, and the callbacks registered at that moment run as at any boundary, seeing the input as the last messages. Their results apply by the seam's rules; with the input alone the change is an append, which needs no compaction reset. A callback that returns `"end"` there, or an `end()` after the wake, ends the member `stopped`: the wake cleared the answered mark, so it has not answered in this activation.

The idle hold is a hold in every sense the seam defines ([swarm-turn-seam.md Time](swarm-turn-seam.md#time)): `held` is true, the member time limit is paused, `swarm_wait`'s all-waiting check counts the member as not active, and `holds` and `held_time` count it. A persistent member's limits (token, cost, turn, message, time) and its share of the swarm's caps are entered once by the member wrapper and span all its activations, with idle time free for the member time limit; the conversation, and with it the message limit and the context window, grows across activations, with the member's compaction working on one loop throughout.

## Keys and verdicts

With a result contract that has an `answer_key` or a `verifier` ([swarm-scoring.md The result contract](swarm-scoring.md#the-result-contract)), each answer is a submission for the contract. It is keyed when it is given and verified as it arrives, on the same serial path as a non-persistent member's submission, while the swarm runs, so a verifier that calls a model can still call it. Nothing is keyed or verified again when the member ends. The kinds of contract are treated alike: an `artifact` task's verifier checks the environment at each answer, as it does at each submission.

- **The key.** `_answer()` keys the answer after it has recorded it, written its `answer` event and settled the provisional answer, as `_end()` keys a non-persistent submission after its end is recorded: `answer_key(output.completion)` on the recorded copy, refused with a `TypeError` unless it is a `str` or `None`. The runtime then settles the provisional answer again, since the key can change `vote`'s answer, as `_end()` does after keying a submission. The key runs inside the member's loop, where the member's wrapper reads a sourceless custom `LimitExceededError` as the agent stopping itself (`_call_agent()` in [`_member.py`](../src/inspect_swarm/_member.py) ends it `member_limit:custom`, bare or in a group of such errors only), so a key that raised one would end the member quietly with its answer kept. `_answer()` therefore catches any `Exception` from `key_answer()` (the key's own error, or the `TypeError` for a value that is not a `str` or `None`) and raises `AnswerKeyError` from it, a private `RuntimeError` subclass in `_controller/_control.py` whose message names the member and the answer's index, and which no classifier consumes. It propagates out of `after_answer()` through the member's loop before the answered mark is set, so the member ends `errored` and the sample fails with `AnswerKeyError`, the key's error its `__cause__`, as for an answer whose output is refused; the answer stays recorded, with no key. A `BaseException` that is not an `Exception`, a cancellation among them, is not caught. The agent's own self-stop, raised by its tools or loop rather than by the key, is unchanged.
- **The verdict.** With a verifier, `_answer()` then puts the answer on the runtime's verification queue, behind the submissions and answers already on it, marks the member *checking*, and notifies, unless the hard stop has already ended verification. The queue's task calls the verifier with the answer's completion and the sample's metadata, one call at a time, in the swarm's span and under the runtime lever, and records the verdict and its swarm time on that answer, with a `verdict` event that carries the answer's index. Everything [swarm-scoring.md Verdicts](swarm-scoring.md#verdicts) says of a submission's verification holds for an answer: the checks on what the verifier returns, its errors, verification through grace, a call the stop's closed lever or a reached cap refuses, the hard stop, and a verdict returned after a cancellation. Finalisation alone differs: it never verifies an answer, so one the queue settled without a verdict stays unverified ([swarm-scoring.md Verdicts](swarm-scoring.md#verdicts)). When the queue has settled the answer, with a verdict or without one, the member is no longer checking.
- **The verifier's time is work.** While an answer is checking, its member's hold is inside `suspend_working_limit()`, which marks the sample as waiting, so a verifier whose time no other scope marks (plain Python, such as a format check, or work it runs in a thread) would be charged nothing and could escape the sample's working limit. `_take_verdict()` therefore calls the verifier inside Inspect's `known_work()`, as the gate calls a boundary callback (`_seam.py`), so its whole call counts as working time unless the verifier marks its own waits with `suspend_working_limit()`. Only the call is inside it: the queue's wait for the next item and the member's idle hold stay outside. The same holds for a non-persistent member's submission verified while another member is held, since the same `_take_verdict()` serves both.
- **`MemberIdle` waits for the verdict.** When the boundary after an answer admits the hold while the member is checking, the gate holds it as for any admitted hold (its time limit paused, `held` true, the wait inside `suspend_working_limit()`), but the runtime leaves it `running`, queues no `MemberIdle` and marks the hold *admitted*. When the queue settles the answer, the runtime sets the member `idle` and queues `MemberIdle(member, answer, news, verdict)` in one synchronous step, provided the hold is still admitted and held and neither a stop nor an end request has reached the member; otherwise the member is ending through its lever and is not published. `news` is computed when the event is queued, so a write during the wait is in it.
- **One answer in flight.** `wake()` accepts only an `idle` member, and a member becomes `idle` only once its latest answer is settled, so a persistent member has at most one answer on the queue, every `MemberIdle` carries the verdict on the answer it names, and no wake overtakes a verdict. A verifier slower than the controller delays the member's next activation by its own time, as it delays a submission's `MemberEnded`.
- **A stop or `end()` during the wait.** The member is held, so the stop or the end request cancels its hold, as for any held member, and it ends `submitted` with the answered mark set. Its `MemberEnded` then waits for the answer's verdict as a non-persistent member's waits for its submission's: the member counts as live, *verifying*, for `events()` and for the stop procedure until the queue settles the answer.
- **No verification at the end.** `_end()` keys and puts on the queue only a non-persistent member's submission. A persistent member that ends `submitted` has its last answer as its output, keyed already and verified or on the queue, so its `MemberEnded` waits for that answer's verdict when it is still checking, and otherwise is queued at once. An output it returned in any other ending is not an answer and is neither keyed nor verified.
- **What a controller sees.** A persistent member's `MemberHandle.verdict` is the verdict on its latest answer, as a `VerdictSummary`: `None` before its first answer's verdict is taken, while its latest answer is checking, and when that answer was left unverified. That is the answer `choose_answer()` takes. `MemberIdle.verdict` is the verdict on the answer it names. `MemberEnded.verdict` is the handle's verdict when the event is queued, whatever the status: the member's answers stay candidates however it ends, so a member stopped after a wake reports the verdict on the answer it gave before. Without a verifier all three are `None`, and `MemberIdle` is queued at admission.
- **`member_scores`** grades a persistent member that ended `submitted` on its last answer, its output, so the per-member metadata's `answer_key` and `verdict` are that answer's, from the last `answer_results` entry, or both `None` when the list is empty (a record written before it existed, which re-scoring still grades, without running the key or verifier); for a member that ended any other way they stay `None`, since its output is not a recorded answer. `_member()` in [`_member_scores.py`](../src/inspect_swarm/scorer/_member_scores.py) reads them.
- **The record.** `MemberResult.answer_results` holds one `AnswerResult` per answer, in the order of `answer_times`: its `answer_key`, `verdict` and `verdict_time` ([swarm-scoring.md Persistent members](swarm-scoring.md#persistent-members)). A persistent member's own `answer_key`, `verdict` and `verdict_time` are `None`, as its own `time` is not an answer's time.

## States

`MemberState` is `pending`, `running`, `idle`, `ending` or `ended`; only persistent members are ever `idle` or `ending`.

| From | To | When |
|---|---|---|
| `pending` | `running` | `start()` |
| `running` | `idle` | the boundary after an answer has admitted the hold and, with a verifier, the answer's verdict is settled, whichever comes second; `idle` is set and `MemberIdle` queued together (at admission without a verifier) |
| `idle` | `running` | `wake()` |
| `idle` | `ending` | `end()` or a swarm stop, synchronously, in the call |
| `running` | `ending` | the boundary after an answer refuses the hold, before the gate ends the member |
| `running`, `ending` | `ended` | the member wrapper's end, which queues `MemberEnded` |
| `idle` | `ended` | a cancellation from outside the swarm (the sample's limits or interrupt) reaches the idle wait |

A member is never `idle` before its hold is admitted and its latest answer's verdict is settled, so `MemberIdle` reports an admitted hold, with its verdict, when it is published. Answers are separate from the state: an answer is recorded in `after_answer()`, before the boundary, and stays a candidate however the member ends, a refused admission included. The answered mark, set by `after_answer()` and cleared by `wake()`, is what the member wrapper reads when it classifies a stop or an end: a member ended by its lever while the mark is set ends `submitted`, whether it was `idle` or not yet admitted.

- **Availability.** `wake()` accepts only an `idle` member. A member between its answer and its admission, or admitted while its answer is checking, is `running`, and one whose admission failed or that is ending is `ending`; both refuse new work.
- **Liveness.** `events()` counts a member as live while it is `running` or `ending`, or *verifying*: ended, with its `MemberEnded` waiting for a verdict (a non-persistent member's submission, or the answer a persistent member was checking when a stop or `end()` reached it). So a member whose ending has begun keeps the iterator open until its `MemberEnded` is queued.
- **Addressed records.** The bus refuses a record addressed to an `ending` member ("<name> is ending.") as it refuses pending and ended recipients, since that member can no longer be woken to read it. An `idle` member receives addressed records; it cannot send or call a channel tool, since only a running member's tools deliver.
- **Stopping.** The stop closes the levers of running and idle members and sets idle ones `ending`; its grace and hard stop, and an `end()`'s grace, wait for and cancel every member that has started and not ended, `ending` ones included.

## Waking

`SwarmControl.wake(member, input)` is synchronous, as `start()` is. It looks the member up (`KeyError`), builds the input's messages (`ValueError` for an empty string, an empty list, or a list holding anything but a `ChatMessageUser`), refuses once the swarm is stopping (with `start()`'s stopping refusal, so a controller that meets it ends with the stop) and refuses a member that is not `idle` (`RuntimeError`, saying why: not persistent, not started, still working, not yet held or its answer still being verified, ending or ended). Every refusal comes before the member changes, so a refused wake leaves it idle. It then sets the member `running`, clears the answered mark, counts the activation, hands the input to the waiting boundary, settles the record and notifies.

**Every wake message is a copy with a fresh id and no `source`.** A string becomes a new `ChatMessageUser`; each message of a list is deep-copied with a new shortuuid id and `source` cleared, and the caller's messages are not changed. A controller may reuse one list for every wake. With the caller's ids, a second wake would repeat ids the conversation already holds, breaking the seam's rule that a conversation's ids are unique ([swarm-turn-seam.md The callback contract](swarm-turn-seam.md#the-callback-contract)), and compaction, which sends only messages whose ids it has not processed, would silently leave that activation's input out. `source="input"` marks only the starting input: trimming and compaction keep input-marked messages in a preserved group ahead of the conversation, so a marked wake message would move ahead of the earlier activations' history.

**Wake input is user messages only.** The model does not continue from its own answer, and the change at the boundary is always an append. A system message would count as a rewrite, and react's compaction restores system messages only from the prefix it saved at loop start, so an appended one would be lost. The input is eval-author text, as `start(input=...)` is; the swarm adds no message of its own. A controller that needs another shape of change registers an `on_boundary()` callback, which runs after the wake.

## News for idle members

An idle member is not in a tool call, so nothing tells it of channel changes; the controller is told instead.

- **The member's own loop.** `MemberContext.loop_span` is the agent span of the loop that bound `swarm_tools()`, recorded at the binding. For a persistent member that is its turn loop (the reader rule refuses the rest in a swarm with a waiting channel), whose views clear its news. The member's idle query is `WaitSpec(id=f"idle-{name}", member=name, loop=loop_span, own=True, path=None)`: what a whole-board `swarm_wait` of that loop would watch. A member none of whose loops bound `swarm_tools()` has no query and gets no news.
- **`MemberNews`.** At step 4 of every delivery, after the waits are told, if the record has `wake` set and its channel is a waiting channel, then for every idle member other than the sender for which the channel's `wakes(idle_spec, record)` holds, the runtime queues `MemberNews(member, channel, record, sender)` and notifies. This covers a `shared_memory()` write and a message sent to the idle member with `wake=True`. A `wake=False` record raises no event; the member sees it when it is next woken and looks.
- **`MemberIdle.news`**, computed when the event is queued, reports whether any waiting channel's `news(idle_spec)` has unviewed changes, including writes that arrive while its answer is checking.
- **`notify`.** The shared memory's `delivered` evidence lists idle members with a bound loop among the members a record is news to, since their own loop sees it when woken.

Events can be stale when the controller reads them: two writes give two `MemberNews`, and the first wake makes the member `running`. A controller checks `swarm.member(name).state == "idle"` before it wakes; `wake()` on a member that is not idle raises. `MemberNews` does not say what a record is about, so a controller that wakes on news filters by `sender` or by its own policy, and a worker that is woken with nothing new to do should answer at once. A member that leaves a file unviewed is reported with `news` set every time it goes idle, a file its own subagent wrote included (`MemberIdle.news`, unlike `MemberNews`, does not exclude the member's own writes, since what is news is tracked per loop), so a worker's prompt tells it to view what the status line names before it answers; `examples/lead_and_workers.py` states that protocol.

## Quiescence

`events()` ends when no member is live and no event is queued, where live is `running`, `ending` or verifying (ended, its `MemberEnded` waiting for a verdict; [States](#states)). An idle member is not live, so the iterator ends when every member is pending, idle or ended, no ended member is still verifying, and nothing is queued: the swarm is quiescent. Quiescence is stable against the members' own work: only a running member's tools deliver records, and an idle member has no background work running (its hold is refused while it has any), so no member's work can queue an event until the controller calls `start()`, `wake()` or `end()`. A swarm stop still can: the swarm's time cap stops the swarm on its own, which cancels the controller and ends idle members, each queuing its `MemberEnded`, and a cancellation from outside the swarm (the sample's limits or interrupt) ends idle members `cancelled` along with the controller. A controller that has handled every event and wakes no one returns the stop reason `quiescence`. There is no `Quiescent` event: the iterator's end says it.

`ending` is what keeps a finishing persistent member live until its `MemberEnded` is queued. Ending an idle member, or refusing a hold, only begins the ending: the member's task unwinds later, and only then does the wrapper mark it `ended` and queue `MemberEnded`, or, when the member was checking, mark it `ended` and *verifying*, which keeps it live until the queue settles the answer and queues its `MemberEnded`. A controller that calls `end()` on its only member after `MemberIdle` and goes on iterating receives that member's `MemberEnded` before the iterator ends.

**`leaderless`** treats a `MemberIdle` as a submission: when it stops at the first submission (by default, under a chain led by `first`) it stops on the first one, as on a submitted `MemberEnded`. When its iterator ends it returns `quiescence` if any member is idle, else `all_done`. It never wakes a member, so under `leaderless` a persistent member answers once and stays idle until the stop.

## Endings

| How a persistent member ends | Status | Its answers |
|---|---|---|
| A stop or `end()` while idle, or at the boundary after an answer | `submitted`, its last answer as its output | all candidates |
| A stop, `end()` or a callback's `"end"` while woken or working | `stopped`, as the seam rules | those recorded, candidates |
| Its own limit, a swarm cap or the hard stop, a time limit already reached at the boundary after an answer included | as for any member (`member_limit:time` for that one) | those recorded, candidates |
| Its agent returns after an end request | `stopped` | those recorded, candidates; the final one is not recorded |
| Its agent returns otherwise: an output the gate did not count at an answer exit, a third consecutive refusal, an unrecoverable overflow, or a cut-off | `unsubmitted` | those recorded, candidates; the returned output is never recorded |
| A board read only by a subagent, in a swarm with a waiting channel | `errored`, with the gate's `RuntimeError` | recorded provisionally; the error fails the swarm, so nothing is finalized |
| Background work running at the boundary after an answer | `errored`, with the seam's `RuntimeError` | recorded provisionally; the error fails the swarm |
| A cancellation from outside the swarm while idle | `cancelled` | those recorded; the swarm is cancelled, so its final step does not run |

**A persistent member's normal return is never `submitted`.** Without an end request (the seam's `stopped`) or a self-stop (`member_limit:custom`), the wrapper ends a persistent member whose agent returned `unsubmitted`, whatever `output_status()` says of the output: every output in the answer form that it counts was held at `after_answer()`, so a loop that returns has stopped without an answer. `unsubmitted` already means a normal return the swarm never takes as an answer; a limit status would claim a limit the swarm cannot see, since an `on_continue` may return `False` for any reason, and an author who wants `member_limit:custom` raises that limit from `on_continue`. Non-persistent members keep the stop-reason rule ([swarm-limits.md Stopping](swarm-limits.md#stopping) defines the status set). When a persistent member ends `submitted`, the wrapper takes its output from its last answer.

## The swarm's answer

Every recorded answer is a candidate, whatever the member's later status: an answer was complete when the member gave it, and a later activation is new work, so a worker stopped mid-task keeps its earlier results. A non-persistent member has one candidate, its output, when it ends `submitted`, at its end time.

- **`first` and `last`** choose across all candidates by swarm time; ties go to roster order, then to the earlier answer. `first` is the earliest answer anyone gave, so a swarm whose workers answer subtasks before the answer that matters needs `last`, `choose_answer()`, or a controller that keeps those workers out of it.
- **`choose_answer(member, reason)`** on a persistent member takes its latest answer at the time of the call and keeps it if the member answers again; it raises `RuntimeError` if the member has not answered, whatever its state. Other members keep the rule that only a member that ended with a submission can be chosen.
- **`verify`** ranks every answer of a persistent member by that answer's own verdict, from `answer_results`, beside the submissions' verdicts: the highest value, then swarm time, roster order and answer order. `verify()` in `_final.py` reads a persistent candidate's verdict from `answer_results[candidate.answer]`.
- **`vote`** counts a persistent member once, by its latest answer, the one `choose_answer()` takes: that answer is its candidate, with that answer's key, and a member whose latest answer has no key abstains, whatever its earlier keys (decision: Ransom, 2026-11-10). For a persistent member, `vote()` takes the key of the last entry of `answer_results` and the candidate with that index.
- **Stopping on a verdict.** `leaderless()`, by default under a chain led by `verify`, returns `verified` at a `MemberIdle` whose verdict passed, as it does at such a `MemberEnded`, since a persistent member's verified answer arrives as `MemberIdle` ([`leaderless.py`](../src/inspect_swarm/_controller/leaderless.py)).
- **`baseline()`** refuses a persistent member with `ValueError`, read from the `member()` record before any builder runs. A baseline's attempt is read from the member's own end, key and verdict, and a persistent member's key and verdict are on its answers instead, so a persistent baseline is not a supported comparison ([swarm-scoring.md Not this design](swarm-scoring.md#not-this-design); decision: Ransom, 2026-11-10). `select_at_k` already refuses a row whose member is persistent, which a one-member `swarm()` can still write ([swarm-scoring.md The analysis helper](swarm-scoring.md#selectk-and-the-analysis-helpers)).
- **The provisional answer** is settled after every answer and every wake, as after every end; the final step appends the chosen answer's output message to the sample's conversation.

## Record, metrics and evidence

The fields are documented for users in [Analysis, Persistent members](../docs/analysis.qmd#persistent-members) and [Metrics](../docs/analysis.qmd#metrics):

- **Member record.** `Member.persistent`, serialized into the plan step only when `True`, so other members log as they did without the field.
- **Result record**, version 1 with defaulted fields: `MemberResult.persistent`; `MemberResult.answer_times`, the swarm time of each answer in order, empty for other members, whose answer is their submission at `time`; `MemberResult.answer_results`, each answer's key, verdict and verdict time in the same order, empty for other members ([Keys and verdicts](#keys-and-verdicts)); `FinalRecord.answer`, which of the chosen persistent member's answers is the swarm's, from 0, `None` otherwise. The final `SwarmEvent` carries `answer` too.
- **Metrics.** `MemberMetrics.activations` (1 at start, one more per wake), `answers`, and `awaiting_work_time`, the part of the seam's `held_time` spent `idle`, waiting for a wake or an end; all 0 for other members. A hold admitted while its answer is checking counts in `held_time` from the admission and in `awaiting_work_time` only from the moment the member is set `idle`: the runtime gives the gate that moment, and the gate's idle wait adds the time from it to its own end, nothing when the member was never published. The wait for the verdict is in the record as `verdict_time` less the answer's time. (`idle_time` is `swarm_wait`'s.) `running_time` stays start to end.
- **`steps_to_answer` and `critical_steps_to_answer`** end, for a persistent member's answer, at that answer's `answer` event: `steps_to_answer` counts the member's completed model calls placed before it, and the critical path takes the event as its end node ([swarm-critical-path.md Where the answer ends](swarm-critical-path.md#where-the-answer-ends)). A resumed sample records no positions, so it has no value there.
- **Evidence.** One `answer` `SwarmEvent` per recorded answer, in the member's span, with only `answer` (its index); with a verifier, one `verdict` event per verdict taken on an answer, in the swarm's span, with `answer` set to that index; the answer's time is in `answer_times`, its activation equals its index, and its text is in the member's conversation and `ModelEvent`s. Each admitted idle hold writes the seam's `boundary` event, callbacks or not, with the seam's outcomes (`continue` on a wake, `stop` or `end` when the member ended idle, `cancelled` for an outside cancellation) and a `held_for` covering the whole hold; the wake's input is a `changed` event with origin `swarm` before the callbacks' own. A refused admission writes no `boundary` event: the member was not held.
- **The ledger** keeps one line per member, with its usage across all activations and its final status.

## Decisions

- 2026-10-29: `after_answer()` stays private to inspect_ai, as the gate's `before_turn()` is; only inspect_ai's own loops can persist, and a custom-loop member is refused (decision: Ransom, 2026-10-29).
- 2026-10-29: a recorded answer stays a candidate however the member later ends, a refused admission, a stop mid-activation and a cut-off included (decision: Ransom, 2026-10-29).
- 2026-10-29: every answer of a persistent member is a candidate for `first` and `last`, not only its latest (decision: Ransom, 2026-10-29).
- 2026-10-30: an answer counts only in the loop's own answer form, a submit call or a `react(submit=False)` tool-free reply (decision: Ransom, 2026-10-30).
- 2026-10-30: a submitting turn that also calls a handoff is never recorded as an answer, accepting that a genuine submission beside a handoff costs the member that answer rather than risking a child's result or classification as the parent's (decision: Ransom, 2026-10-30).
- 2026-10-30: a cut-off ends a persistent member `unsubmitted`, its output never recorded and its earlier answers still candidates (decision: Ransom, 2026-10-30).

## Alternatives considered

**A `submit=False` member protocol.** Members would run `react(submit=False)` with a swarm `report` tool that records an answer, and an `on_continue` that returns the state after a reply so the seam sees an `after == "reply"` boundary. It needs no inspect_ai change beyond the seam, but a standard `react()` worker, with its submit tool and prompt, could not persist: its author would rebuild it with another prompt and stop condition and wire a swarm-specific hook.

**Clean re-entry.** The member wrapper would call the agent again on the state it returned, with an inspect_ai change so `react()` does not insert its system prompt twice. It would also cover custom agents that return. But each activation opens a new loop: the seam binds one loop per member and refuses a second when callbacks are registered (decision: Ransom, 2026-10-29), compaction would be initialized again for each activation, MCP connections and the agent channel would be reopened, the bus's loop binding would point at a closed channel, and a re-entered `react()` duplicates its system message and has removed the submit tool's results.

**Letting the gate wait inside `after_answer()`.** It saves the step to `before_turn()`, but the hold would happen outside the seam's boundary: no `Boundary` for callbacks to see the woken member before its first generation, and a second place for the stop, time and evidence rules.

**A public `AgentChannel.after_answer()`.** It would let a custom loop persist too, but no member loop in use needs it, and a custom loop is refused loudly. It can be made public when one turns up.

**Recognizing loops by registry name.** A name says nothing about what a member runs (a builder retags the loop with its own name) and does not prove the agent is the loop when it matches (a `functools.wraps` copy carries it). The mark, tied to the running wrapper and its `__wrapped__`, does both.

**Keeping the caller's ids on wake input**, refusing a list whose ids repeat each other or the conversation's. The refusal would have to see the member's compaction state, which lives in its loop, and a controller reusing a message list would meet an error for an input that is harmless with fresh ids.

**A controller-level switch** (`Controller(persistent=True)`, or a `hold()` a controller calls after `MemberEnded`). One switch for a whole roster, but a lead and its workers differ, and a hold after the end comes too late: the loop has returned. The member record's field is logged with the arm.

**Only the latest answer is a member's candidate.** Simpler to state, but `first` would then depend on later work, and the earliest answer could never be the swarm's.

**Not recording an answer during a stop.** A member that answers in the grace period would end `stopped`, its answer lost, where a non-persistent member's submission in the grace counts.

**Other endings for a cut-off.** Classifying it by its output's stop reason, as for one-shot members, would make a turn limiter's last output an answer, and with `last` the swarm's over the member's real earlier one. Failing the member `errored` would fail the whole swarm on an ordinary turn limit. `member_limit:custom` would claim a limit the swarm cannot see.

**A `Quiescent` event, or a `quiescent()` channel hook.** The iterator's end already says no member is live and nothing is queued. A channel hook is for channels whose state can keep a swarm going with no delivery, such as a task list with open tasks; none exists.

**Waking members on news in the runtime.** The bus would wake an idle member on any `wake=True` record. It takes the decision from the controller, and in a large swarm every write would wake every idle member ([swarm-wait.md Room for later work](swarm-wait.md#room-for-later-work)).

**Publishing `MemberIdle` at admission and the verdict later**, as a `MemberVerdict` event or a second `MemberIdle`. The member would be available sooner, but a controller could wake it before the verdict on the answer it just gave, its next answer could reach the queue first, and a controller deciding whether to wake on a verdict (retry on a failed check, stop on a passing one) would have to pair two events. Holding the publication keeps one event per answer, with its verdict, as `MemberEnded` already waits for a submission's.

**Keeping the member `idle`, with only its event delayed.** `wake()` would then accept a member whose `MemberIdle` the controller has not yet seen, from a controller that polls states or wakes on `MemberNews`, and the verdict could arrive after the member had begun its next activation. A checking member stays `running`, which `wake()` already refuses with a reason.

**Keying in the verification queue** rather than in `_answer()`. The key's error would then fail the swarm from the runtime's task instead of the member's, but a key-only contract would need the queue's task too, and the key would wait behind every verifier call ahead of it. The key is a pure function of the completion, so it is taken where `_end()` takes a submission's: at once, after the answer is recorded.

**Keys and verdicts as lists beside `answer_times`** (`answer_keys`, `answer_verdicts`, `answer_verdict_times`). One list of `AnswerResult` keeps an answer's values together.

**Filling a persistent member's own `answer_key` and `verdict` from its last answer.** Readers of one key per member would keep working, but each value would be in the record twice, and only for a member that ended `submitted`. The member's own fields describe the submission at `time`, which a persistent member does not have, as `answer_times` already says.

**Counting the wait for the verdict in `awaiting_work_time`.** It needs no time from the runtime, but the metric would then mix the verifier's time with the controller's, which is what it exists to measure; the verdict's wait is `verdict_time` less the answer's time.

## Compatibility

- **inspect_ai.** No public API: the private gate module's `after_answer()`, `TurnLoop`, `mark_turn_loop()` and `turn_loop()`, the private `TurnGate` entry point, and `_call_tools`'s `watch_handoffs()`, which `execute_tools()` reports to only when it is installed. The react loops behave as before without a gate.
- **Member records.** `persistent` defaults to `False` and is serialized only when `True`, so existing members log, rebuild and replay as before.
- **Controllers.** `ControlEvent` is `MemberEnded | MemberIdle | MemberNews` and `MemberState` has `idle` and `ending`, but only swarms with a persistent member produce any of them; a controller reads an event's type before its fields ([Writing a controller](../docs/controllers.qmd#writing-a-controller)). `MemberHandle` has `persistent` and `answers`, which a structural implementation of the protocol must provide (`False` and `0` for other members). `Boundary` has a required `activation`; only the gate builds it. `MemberIdle` has `verdict`, defaulting to `None`, so code that builds one positionally or by keyword is unchanged. A persistent member's `MemberHandle.verdict` and `MemberEnded.verdict` show its latest answer's verdict.
- **Result contracts.** `verify`, `vote` and `leaderless`'s stop at a passing verdict read per-answer keys and verdicts only for a persistent member, so a swarm without one chooses and stops as it would without them.
- **`baseline()`** refuses a persistent member; nothing in this repository, its examples or its docs passes one.
- **Logs.** The record, final event, metrics and `boundary` event fields have defaults, so logs without them load unchanged; the `answer` kind is one more `SwarmEvent` kind, which the viewer shows as any other; the `verdict` event's `answer` is `null` for a non-persistent member's submission, as the `final` event's is. The record is read through `swarm_result()` ([Scoring, The result record](../docs/scoring.qmd#the-result-record)) and has no generated TypeScript type.
- **Swarms without persistent members.** Unchanged: no member is ever idle or ending, so the stop's "started and not ended" set is the running set, the iterator's live set is the same, and the shared memory's `notify` lists the same members.

## Security

- **Wake input is eval-author text** in the user role, as `start()`'s input is. No member text reaches a controller: `MemberIdle` and `MemberNews` carry roster names, indices, bus record ids, channel names and a flag. `MemberNews.sender` is the writer's roster name, which a controller can already see on `MemberEnded`; in a swarm where members choose their names there are no channels with records, so no news ([swarm-chosen-names.md](swarm-chosen-names.md#what-is-refused-and-why)).
- **Model output in the evidence.** The `answer` event carries an index; the wake's `changed` event carries ids and hashes. No model text reaches either.
- **`MemberNews` is never about a member's own writes, and cannot flood the controller unchecked.** It excludes the sender; every write that can raise it passes the channel's storm controls and limits first; each event is a few small fields. A member can try to induce its peers' wakes by writing, which is the controller's policy to filter, by `sender` or otherwise.
- **`MemberIdle.news` has no sender exclusion.** It asks the channels whether the member's own loop has news, and the shared memory tracks what each loop has seen, so a write by one of the member's own subagents is news to its parent until the parent views it. A member whose subagents write to the board, and whose controller wakes on `MemberIdle.news`, is reported with `news` set at every idle until its top-level loop views those files, with no new delivery; the worker protocol in [News for idle members](#news-for-idle-members) applies to its subagents' writes too.
- **The answers are model output**, kept as `ModelOutput` copies in the runtime and scored as submissions are; the swarm itself parses none of them.
- **Each answer reaches the contract's code.** `answer_key` and the verifier get each answer's completion, as they get each submission's: task code that must accept any text, and a verifier that runs code only in the sandbox ([swarm-scoring.md Security](swarm-scoring.md#security)). An answer's key and verdict explanation reach only the record, written when the swarm ends, and are kept as a submission's are. A controller sees an answer's verdict only as `VerdictSummary(passed, value)` on `MemberIdle`, the handle and `MemberEnded`, never the explanation, so no member text reaches it through a verdict.

## Not this design

- **A built-in `coordinator` controller** and the `lead_done` topology reason ([swarm-api.md Controllers](swarm-api.md#controllers) sketches it). Controllers that wake members are the eval author's code.
- **Idle members in `swarm_wait` results**: telling a waiting lead that a worker went idle, as its result names ends. Today the lead hears of it only through the worker's writes or the all-waiting release.
- **A `quiescent()` channel hook**, for a channel whose state can keep the swarm going without a delivery.
- **Per-activation limits**, and scores per answer: `member_scores` grades a member's output, which for a persistent member that ends `submitted` is its last answer ([swarm-scoring.md Member scores](swarm-scoring.md#member-scores)).
- **A public `after_answer()` hook** for custom member loops, if one turns up.
- **Persistent members whose board is read only by subagents**, in a swarm with a waiting channel, which needs news defined for the member across its loops (a member-level seen state in the shared memory) rather than for one loop.
- **Persistent wrapped agents**: a member whose agent calls a loop and then checks or changes its result (`checked_solver()`, `prover()`) would need the wrapper's completion logic to run at each answer, before it is recorded.
- **react's submission detector accepting a child's same-named tool result** in ordinary loops, which a handoff without the `content_only` filter can bring back; this design only declines to record a submission from a turn that called a handoff.
- **`on_continue` cut-offs of non-persistent members**, which end `submitted` by their stop reason, so a `TurnLimit`-limited one-shot `react()` member reads as a submission and can be the swarm's answer under `first`. Applying the answer-form rule to them would need the loops to report their exit outside a persistent member's gate.
- **Persistent bridged members**, through inspect_swe's `--resume`, and **persistent members with background work**, which needs holding background work ([swarm-turn-seam.md Not this design](swarm-turn-seam.md#not-this-design)).
- **Delivery to pending members**, and starting a member on its first message.
