inspect_swarm

Swarms, members, controllers, channels, results and the budget view.

Swarms and members

swarm

A swarm of agents working on one sample.

Each member gets a timeline in the sample named after it, so member names must be unique across the swarm runs and other timelines in a sample. To run swarms more than once in one sample, build them with distinct member names. A member may not be named init, solvers or scorers: Inspect’s timelines read spans with those names as the sample’s phases.

member

A swarm member, with a name, role, limits or count.

A member is a built agent, member(react(prompt=...)), or a registered @agent factory and its arguments, member(deepagent, args={"tools": [bash()]}, count=4). Both must be registered with @agent, so that the log can name them and replay can find them. A built agent can also be passed to swarm(members=...) without member().

No agent object runs twice at the same time in one sample. A built agent is one member: it is built once, when the task is built, and shared by concurrent samples, as any Inspect solver is. The same agent object cannot be in two members. Several copies of one configuration (count above 1) need the factory form: the swarm calls factory(**args) once for each member in each sample, so each copy gets its own agent and whatever the factory builds. member() checks the arguments against the factory’s signature but does not call it, so the factory’s own checks run when the member is built.

Names. Members left on their default name are numbered across the whole roster, not per record, so one member with different arguments takes two records: [member(react, args={"prompt": a}, count=6), member(react, args={"prompt": b, "model": m})] is react-1 to react-7. When every copy differs, give each its own record, as in [member(react, args={"prompt": p}) for p in prompts]. Names given with name are not numbered across records, so give each record its own.

Objects given to an agent are shared. Every member built from one record receives the same objects from args, and two built agents given the same tool object share it, across members and samples. Inspect’s built-in tools keep their state in the sample store or the sandbox, so this matters only for a custom tool or helper that keeps state in its Python object (a counter, a cache, a client). To give each member its own, construct it inside a member builder, an @agent factory that builds the configured agent, and use the factory form.

Tool state. Each member runs in its own tool-state scope, named after the member. Built-in tools that keep state in the sample store (memory(), bash_session(), the skill tool) give each member its own state when their instance is left at the default, so the default memory() is private to each member. An explicit instance is used as given: members, or the copies of one counted member, that name the same instance share its state, so a board shared on purpose is memory(instance="board"). The sample store itself is shared. State that custom tools or agent code keep in the store with no instance is shared unless they resolve their instance with tool_state_instance(). Built-in tool state that a setup solver prepared at the default instance before the swarm runs is not visible to the members.

Submissions. A member that returns normally has submitted, and its output is its answer, unless the output’s stop reason is content_filter or model_length. That is how react() returns after three refusals or a context overflow it could not recover from, so the member ends unsubmitted and the swarm never chooses its output as the answer. Other agents keep the rule that a normal return is a submission: an agent that gives up in some other way and returns is treated as having answered. A persistent member’s normal return is never a submission: its answers are recorded as it gives them, so a loop that returns has stopped without one (an on_continue that returns False, for example), and the member ends unsubmitted, its earlier answers still candidates.

Persistent members. With persistent=True, the member stays available after it answers: when it submits in a turn that calls no handoff, or a react(submit=False) member gives a tool-free reply, the swarm records that as one of its answers and holds the member idle at its next turn boundary, in the same agent loop. The controller hears MemberIdle and gives the member its next piece of work with SwarmControl.wake(), which appends it to the member’s conversation. Every answer is a candidate for the swarm’s answer. The member’s limits span its whole life, and its time limit does not run while it is idle. A member stopped or ended while idle ends submitted, its last answer as its output. Only a member whose agent is a react(), react(submit=False) or deepagent() loop without background dispatch, given directly or returned by an @agent builder, can be persistent; any other agent, and a bridged member, is refused.

Stopping itself. An agent that raises LimitExceededError("custom", ...) with no source to stop itself ends only its member, with status member_limit:custom; the other members continue and the swarm never chooses its output as the answer. This holds when the error is raised in a task group inside the agent, too.

Sandboxes. Members share the sample’s sandbox by default. With sandbox, a member works in its own: the swarm makes that environment the member’s default, so sandbox() in its tools returns it, and hides the sample’s other environments from the member except those in visible_sandboxes, such as a shared service. Tools that choose a sandbox without a name, such as text_editor(), bash_session() and the agent bridge, use the member’s own; a visible service is reached only by name. sandbox="{member}" gives each copy of a counted member the environment named after it: member(factory, name="agent", count=2, sandbox="{member}") runs agent-1 and agent-2 in the environments of those names. The sample’s sandbox configuration provides the environments (for Docker, a compose service for each), and the swarm checks that they exist when it starts. When one member has its own sandbox, every member must have one, no two the same, and the filesystem channel, which describes a shared sandbox, can be used only as filesystem(shared_volume=True), for sandboxes that each mount one shared volume. A service in visible_sandboxes is reachable from any of the member’s tools that take a sandbox name, so list only services every member may use.

Chosen names. With choose_name=True the member is not told its name: the swarm’s preamble says how many agents are in the swarm and asks it to choose a name for itself and tell the other members, and the filesystem channel tells it to keep its work in a directory named with the name it chose. Its role, if it has one, is still stated. The swarm’s records, spans, tool-state scopes and budget shares still use name. A swarm in which any member chooses its name can use only the filesystem channel or no channel (channels=[]), since other channels show members to each other by name. Text you give the member yourself is not changed: the sample input, a controller’s start(input=...) and start(preamble=...), the agent’s prompt and the sandbox configuration. A controller’s start(preamble=...) uses its text as given, and preamble=False leaves the preamble out; neither adds a request to choose a name.

Scoring with member sandboxes. The task’s scorers run after the swarm, outside every member, where sandbox() is default. A scorer that grades the members’ work names each member’s sandbox itself, as in sandbox("agent-1"), and the sandbox field of each member in the swarm’s result record says which member used which.

Background work belongs to the member. Work its agent starts with background(), such as deepagent(background=...) subagents, spends through the member’s limits and share, and is the member’s in the ledger. When the member’s agent returns, the swarm stops the background work from starting model calls, gives it the swarm’s grace period to finish calls and tool calls in flight, and cancels what is left. The member ends after that, with the status its agent ended with; Budget.grace=0 cancels background work at once. A member time limit bounds its agent only: after the agent returns, its background work gets the grace period too, and the cancelled work’s cleanup is awaited. Background work must be started by the agent while it runs; a factory that starts it while building the agent makes the member errored. A sourceless custom limit error raised in background work ends only the task that raised it; the member’s agent and its other background work continue. Work started outside background() (an asyncio task, a process left running in the sandbox) is not stopped. Bridged members cannot have background work: background() raises in a member declared or found bridged, and a member that uses the agent bridge after starting background work (through a bridged subagent, for example) is cancelled and ends errored.

ACP agents, which wait for their caller to drive them rather than returning, are refused: a built one when member() is called, and a factory’s when the member is built.

Controllers

leaderless

Start every member with the swarm’s input; stop at the first submission, or when none is still working.

By default the swarm stops when the first member submits. The swarm’s answer is the first submission, so nothing the other members do after it can change the answer. The members still running are stopped: they finish the calls they have in flight, within Budget.grace, and the ones still running after it are cancelled.

A persistent member’s answer is a submission: it stops the swarm by default. leaderless never wakes a member, so with stop_on_submission=False a persistent member answers once and stays idle until the swarm stops.

Pass stop_on_submission=False to let every member run to its end when the other members’ work still matters: tasks whose scorer reads a shared artifact (such as the sandbox) after the members end, where members still working change what is scored; arms that measure each member’s result (team@k); and agents for which any normal return counts as a submission, so that a member that gives up would end the swarm. Add final="last" to make the latest submission the answer, for a team whose members build on each other’s work.

Controller

How a swarm runs: which members start, when and with what input, and when the swarm is done.

A Controller holds configuration only: one object serves every sample, so per-sample state belongs in run’s local variables. Return one from a factory decorated with @swarm_controller.

Start a member, and return at once.

wake

Give an idle member its next piece of work, and return at once.

The member continues its conversation with input appended: a string as one user message, a list of user messages as given. It keeps its tool state, its limits and what it has seen. Each message gets a new id and no source; the messages passed are not changed, so the same list can be passed again.

Methods

on_boundary

Register a boundary callback, called at every turn boundary of the member’s own agent loop.

A boundary comes before the loop’s first generation and before each one after it, with no model or tool call of the loop in flight. The callbacks run there in the order they were registered, in the member’s task, while the member is held: its time limit pauses, swarm_wait does not count it as active, and a stop ends it at once. Each receives a Boundary and returns None to continue, a list of messages to continue with that conversation (it must hold a user message), or "end" to end the member stopped. Registered on a pending member, the callback sees boundary 0, before the first generation; on a running one, from its next boundary.

A callback’s model and tool calls count towards the member’s limits and the sample’s working time, and so does the rest of its time: wrap an idle wait in suspend_working_limit() to count it as waiting. An exception a callback raises ends the member errored. Every change a callback makes is recorded as a changed event, with origin.

Source

The callback.

Names the caller in the evidence, such as orbit or operator: 1 to 64 letters, digits, _, -, . or :. swarm is reserved.

end

End the member stopped, with the reason ended by <origin>.

A held member ends at once: the waiting callback is cancelled, later ones do not run, and no change of theirs is applied. A running member’s next model call is refused and it ends at its next boundary. A pending member ends at its first boundary once started. If the member is still running when the swarm’s grace period has passed since the request (or since a pending member started), its turn or its cleanup included, it is cancelled and ends cancelled. A member whose agent returns after the request ends stopped, whatever its output. A second call, or a call for a member that has ended, changes nothing. The other members and the swarm go on.

Channels

filesystem

A shared directory, with a convention for using it, stated in each member’s preamble.

By default the channel describes the sample’s sandbox, which the members share: a directory for shared files, a notes file members append to, and a scratch directory for each member.

With shared_volume=True it describes members with their own sandboxes (member(sandbox=...)) that each mount one shared volume at shared: shared and the notes file in it are the same directory in every member’s sandbox. There is no scratch directory, since each member’s sandbox is already its own. The swarm cannot check that the volume is mounted in every member’s sandbox; it takes your word for it.

The channel adds no tools and does not create the directories.

shared_memory

A board of files that every member of the swarm, and their subagents, read and write.

Each member gets a shared_memory tool with the commands and parameters of inspect_ai’s memory() over files under /shared_memory. Every write goes through the swarm’s bus as a record from the member that made it. A view shows a file inside a fence that names its last writer and version, and lists of changed files name them by ids such as f-3, which view takes as its file_id. A loop must view a file in its current version before it overwrites it with create, inserts into it, renames it or deletes it. append needs no view: it adds text on a new line at the end of a file, creating the file if it does not exist. changes returns only the list of files other agents changed since the loop last viewed them, which ends every result. That list names at most 10 files at the end of a result, and every file in changes.

A fence is a label for the reader, not a protection: a member can write text that looks like a fence, another member’s file or a status line.

The board lives for one run of the swarm. A result longer than the tool output limit is truncated in the middle, as Inspect truncates any tool’s result.

Each member, and each of its subagents, also gets swarm_wait, which blocks until a file it watches has a change it has not viewed, another member ends, every member is waiting, the swarm stops, or a timeout passes. A wait is wall-clock time inside a tool call: it counts towards the member’s time limit, the swarm’s time cap, and the sample’s time and working limits. It makes no model call, so it adds no tokens, cost or steps.

messages

Direct messages between the members of the swarm.

Each member’s own loop gets three tools. send_message sends a message to a member, to several, or to "all", every other running member, and returns its id, such as m-3. read_messages returns the member’s unread messages, oldest first, each inside a <peer_message> fence that names its id, sender and recipients, and marks them read. list_members lists the roster with each member’s role, state and, once it has ended, its status. The tools of other channels carry no count. Nested loops, such as a deepagent() member’s subagents, get none of these tools, so a member’s inbox has one reader.

Every send goes through the swarm’s bus as a record from the member that made it. A send is refused when an address is not a running member other than the sender, when the message is empty or longer than max_bytes, when a recipient already has max_unread unread messages, when the sender is over its rate, or, with dedupe, when a recipient still has the same text from the same sender unread. A refused send reaches no recipient.

One read always returns at least the oldest unread message whole: the read is bounded by the largest fence the roster allows plus max_bytes, and Inspect’s tool output limit does not apply to it.

A fence is a label for the reader, not a protection: a member can write text that looks like a fence, another member’s message or a status line.

The member’s own loop also gets swarm_wait, which returns while it has unread messages sent with wake=True (the default), and otherwise blocks as shared_memory()’s does, up to max_wait seconds. A wait is wall-clock time inside a tool call: it counts towards the member’s time limit, the swarm’s time cap, and the sample’s time and working limits.

def swarm_tools() -> ToolSource

swarm_bridged_tools

The tools of the swarm’s channels, for a bridged member’s agent.

Pass it in the agent’s bridged tools, claude_code(bridged_tools=[swarm_bridged_tools(["messages"])]). A bridged agent’s tools are fixed when it is built, so name the channels it uses: "messages" gives send_message, read_messages and list_members, and "shared_memory" gives shared_memory. Both also give swarm_wait. The tools are served as the MCP server swarm.

Each tool acts as the member whose agent calls it, and finds the swarm’s channel when it is called; a tool whose channel the swarm does not have returns an error saying so. The CLI is one loop of the member, whichever of its conversations calls: its subagents read the member’s messages, and a message any of them reads is read for all; they share what the member has viewed in the shared memory; and their sends and writes are the member’s. The member’s evidence records these calls with via set to "bridge".

A bridged member never counts as waiting, since one call in swarm_wait does not show that its CLI is idle: its waits end on news, a member’s end, the swarm’s stop or their timeout, never because every member is waiting. A bridged wait lasts at most max_wait seconds, or the longest wait of the swarm’s channels if that is shorter, because the CLI gives up on a tool call that runs too long: Claude Code and Codex both stop one after 300 seconds by default, and the shared memory’s waits last up to 600. Claude Code’s limit cannot be raised for bridged tools, so keep the default of 280 for it. A Codex member whose timeout is raised with codex_cli(config_overrides={"mcp_servers.swarm.tool_timeout_sec": "700"}) can take a matching max_wait.

A swarm with the messages channel needs "messages" here too: other members can send to the member, and without the messages tools it could never read what they send, so the tools of a bridge given only "shared_memory" return an error saying to add it. A member uses these tools or swarm_tools(), never both, in either order: each would be a reader of its inbox.
